# 网页改进分析：RI 与 RSI 经验闭环

2026-10-19。本文件记录本轮对仓库的核查、展示建议和证据缺口；功能要求以 [spec.md](spec.md) 为准。本轮未修改网页或部署服务。

**计划阶段范围更新**：用户已确认 PPA 数据后续提供。本次只交付优化空状态与数据接入边界，不准备三版本 PPA 素材、不搭建测量工具链、不实现收益曲线。下文有关图形及离线测量的建议属于后续接入阶段；当前实施范围见 `spec.md` 的“本次交付范围”。

**导航更新**：用户随后允许按需要扩展页面，不再要求单页。当前方案采用设计工作台、持续优化、经验闭环三个页面，共享案例、常驻对话与证据上下文；原五标签方案已替换。

## 推荐呈现

用两句话讲故事：

- **RI：每一轮实验，都在可验证的约束下寻找更好的设计。**
- **RSI 方向：把成败沉淀为经验，让后续决策有依据，并用新结果修订经验。**

顶部以“设计工作台 / 持续优化 / 经验闭环”作为三个主入口。设计工作台内部保留架构、代码、验证；持续优化和经验闭环有各自页面，右侧共用同一个对话框。先做三个内容明确的页面，不额外增加总览、管理后台或设置中心。

```text
品牌 / 案例选择 / 后台状态
主导航：设计工作台 | 持续优化 | 经验闭环
┌──────────────────────────┬──────────────────────┐
│ 当前页面                  │ 共享 RTL Agent 对话    │
│                          │ 当前案例与证据选择      │
│ 工作台：架构 / 代码 / 验证  │                      │
│ 或                       │ 这条经验实际用过吗？    │
│ 优化：PPA 待接入、RI 流程  │ 有哪些验证依据？        │
│ 或                       │                      │
│ 经验：来源 → 复用 → 验证   │ 回答＋可点击证据        │
│ 一张经验卡＋修订与证据入口  │                      │
└──────────────────────────┴──────────────────────┘
```

这是本次无 PPA 数据的布局示意，不包含虚构成绩。每页一个主要任务，经验详情直接跳到工作台的对应验证/波形。未来有 PPA 后再在优化页加入目标摘要、趋势和选中轮次依据。

## RI：参考什么图，如何讲

可参考 [autoresearch 的进展图](https://github.com/karpathy/autoresearch/blob/master/progress.png)。其 [analysis.ipynb](https://github.com/karpathy/autoresearch/blob/master/analysis.ipynb) 使用每次实验的点、保留/放弃状态和累计最佳阶梯线，适合解释持续尝试如何形成收益；[项目说明](https://github.com/karpathy/autoresearch)介绍了固定评估下修改、评估、保留或放弃的循环。

迁移到 RTL 时，使用本项目自己的指标和规则：

| 元素 | 网页表达 |
| --- | --- |
| 横轴 | 实验轮次，保留真实顺序和失败尝试 |
| 纵轴 | 选定的一项指标，显示单位与改善方向；首选面积，有时序数据再允许切换 |
| 点 | 每一轮候选的真实结果；保留/放弃可区分，失败且无数值的尝试只显示状态 |
| 阶梯线 | 通过功能验证、满足约束并被保留的历史最佳值 |
| 摘要 | 基线、当前合格最佳值、可复算的改善比例，未测功耗显示未测量 |
| 选中详情 | 改了什么、为何保留或放弃、对应 RTL、验证报告、测量报告和真实波形 |

参考项目的画图代码会筛选部分显示区域；本项目不据此省略退化或失败尝试，也不采用它的训练指标、成绩或无限运行策略。面积降低但时序不合格的结果不能更新合格最佳线，功能 mismatch 减少不能当成 PPA 提升。

**当前缺口**：本轮在已有 RTL Agent、网页和四例工作区核查中，没有找到可直接接入的 PPA 循环评估与可比较测量序列。当前 Verilator 仿真证明的是对应测试下的功能结果，并不能产生物理面积、时序和功耗结论。新的真实测量素材需要补充，不能从现有成功率或波形推算。

建议先在适当环境离线准备一个 E203 或其明确命名子模块的基线与两个候选测量，审核后在网页展示真实历史。当前约 2GB 公网机器先承担浏览和问答，不为两部分故事强行开放尚未就绪的重型执行。

## RSI：仓库确实有什么记忆

| 现有材料 | 核查结论 |
| --- | --- |
| `zerorepo/rtl_impl/rtl_memory/store.py` | 文件化长期记忆及索引；同条目更新会覆盖内容，尚不能直接作为完整版本演化审计 |
| `zerorepo/rtl_impl/rtl_memory/distiller.py` | 可从补丁结果提炼成功经验或失败方向，包含来源、适用信号、适用限制等；规划纠正和合并规则也有定义，但需分别核查实际调用与材料 |
| `zerorepo/rtl_impl/rtl_memory/selector.py` | 根据模块、信号和失败上下文选择记忆；有模型选择和后备排序 |
| `zerorepo/rtl_impl/repo_react/tools.py` | 实际补丁评估后调用经验提炼 |
| `zerorepo/rtl_impl/repo_react/context.py` | 检索经验、放入上下文，并提供只读长期经验读取入口 |
| E203 已有 `workspace/rtl_memory/` | 存在 5 条经验文件：1 条成功结果类型、4 条语法失败方向类型；它们是可核查的存档素材，不是复用收益证明 |
| 当前网页对话及 Codex 修复路径 | 对话记录持久化与工程长期经验不同；本次未发现 Codex 链直接调用上述长期经验提炼/选择器的接入，不能据此宣称当前在线 Codex 正在完成该闭环 |

E203 存档根为 `rtl_outputs/e203_exu_alu_system/.zerorepo/workspace/rtl_memory/`。这些文件的来源报告、完整性和真实后续采用仍需审核；头部的模块 pass 不能自动升级为系统级通过。当前经验置信度采用规则赋值，不可转换为实测成功率。

第一版“经验闭环”页面建议呈现：

1. 一条经验卡：遇到什么问题、建议复用什么因果/结构模式、什么时候不适用。
2. 三个证据阶段：**已沉淀 → 后续任务实际使用 → 结果已验证**，缺失阶段照实显示。
3. 一次修订：旧经验为何不够、新版增加了什么适用限制；未再次验证则保留待验证状态。
4. 一个可选对照摘要：相同起始任务与预算下，有/无记忆的实际尝试数和结果。没有该对照就显示“收益待验证”，不添加越来越快的装饰曲线。

“经验越多”不保证“能力更强”。更有说服力的材料是：某次失败形成经验，后续真实任务引用了它，新结果又促成经验修订；确有对照时，再讲效率收益。第一版可使用“RSI 方向 / 经验驱动改进”的表述，不能将记忆存档宣传成模型权重训练或已经证明强意义的递归自我改进。

## 关联现有页面与对话

现有入口在 `web/rtl-demo/src/main.ts`，案例、版本和验证选择已能关联聊天。新增内容应让演示者选中某轮实验或某条经验后，直接问：

- “这一轮为何保留，时序约束满足了吗？”
- “这条经验来自哪次失败，后续任务实际用到了哪里？”
- “记忆是否真的节省了尝试次数，依据是什么？”

回答使用自然语言和可点击依据，不把动作协议或内部配置当作产品介绍。已有代码、验证和波形查看入口继续承担证据展示，避免重复造第二套界面。

优化和经验两个页面分别有自己的准备状态：有真实记忆存档可以先展示存档，有 PPA 报告才画实测曲线；已有聊天能力继续工作，但不能据此宣称完整 RI/RSI 已完成。页面可直接打开、刷新及前进/后退，对话和兼容证据选择跨页保留。

## 进入计划阶段需要落实

- 本次只预留 PPA 待接入边界，未来接入时再选定测量对象、可比较条件、主要目标和报告来源。
- 审核可公开的记忆素材，补齐后续使用与经验修订证据；若选择现有 Codex 后端做新演示，明确其经验读取、采用和更新的实际接入。
- 定义经验的不可变历史内容、同轮验证绑定和公开材料范围，保持访客会话隔离。
- 采用共享 shell 与轻量 hash 路由，明确 URL/会话恢复、原链接兼容和跨页证据跳转；不因拆页新建后端或修改域名职责。
- 将 UI 功能检查、真实测量/经验链验收与线上执行可用性分开，不把占位页或替身数据当成故事完成。
