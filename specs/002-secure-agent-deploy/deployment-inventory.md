# 仓库上传范围与服务器环境梳理

日期：2026-10-16。关联：[部署规格](spec.md)。

本文是基于当前代码的计划输入，不是已实现的打包器或已完成的服务器安装。本轮仅检查本地文件并更新文档，没有上传新文件、读取实际密钥值或修改服务器。

## 1. 发布内容按用途分开

| 内容 | 当前来源 | 处理方式 | 可见范围 |
| --- | --- | --- | --- |
| 前端完整成品 | `web/rtl-demo/dist/` | 上传入口页面、assets、四例cases及发布清单；不能只传index.html | 受保护的design站点 |
| Web后端 | `zerorepo/rtl_web/` | 保留API、会话、问答、worker、运行适配、证据和波形模块 | 后台私有代码目录 |
| Agent运行源码 | `zerorepo/rtl_impl/`、`zerorepo/rpg_gen/base/`、`zerorepo/config/`、`zerorepo/utils/`及实际导入的父包/其他模块 | 根据导入链与动态调用确定完整闭包；首版可保守保留`zerorepo/`运行源码，排除开发及生成目录，避免仅复制Web目录后无法执行 | 后台私有代码目录 |
| 运行资源 | 代码实际读取的提示词、配置模板、解析查询及语法源码 | 保留实际资源，不按扩展名统一删除；维护父包结构与相对路径 | 后台私有代码/构建目录 |
| 四例输入规格 | 下文4个Markdown文件及其实际引用资源 | 必须上传，这是运行输入，不属于可丢弃的开发文档 | 后台输入；按既有规则展示必要内容 |
| 四例受审查历史证据 | 从现有不可变bundle、版本和artifact按引用导出 | 形成独立初始化数据，包含实际需要的RTL快照、报告、波形、索引和引用关系 | 后台持久数据；公开展示项单独导出 |
| 历史修复接口契约 | 各例`.zerorepo/module_planner/outputs/contracts.json`中实际存在且摘要匹配的文件 | 单独列入私有输入；当前修复入口仍按原source路径读取，计划需保留最小路径结构或新增明确映射 | 后台只读输入 |
| 来源审查元数据 | `configs/rtl_demo_e203.evidence.json`、`configs/rtl_demo_cases.evidence.json` | 保留，与当前bundle配套；目前worker、修复契约及波形校验仍依赖它们 | 后台只读元数据 |
| 外部验证材料 | RealBench四例验证器、TB、刺激、参考源码和头文件 | 按第4节选择性部署；不包含在静态站点中 | 后台只读验证目录 |
| 部署与运维工具 | `deploy/rtl_demo/`中目标环境实际使用的模板，`scripts/rtl_demo/release.py`及配套发布/预检脚本 | 只传实际需要的脚本和一份精简运维说明；本地Vite启动脚本不是线上服务入口 | dev准备目录/受限运维目录 |
| 环境安装清单 | `requirements-web.txt`及后续生成的生产Web/Agent依赖锁定清单 | 在服务器新建隔离环境安装；当前Web锁文件含测试依赖，生产清单需单独验证 | 安装材料，非网页资源 |
| 许可与第三方声明 | 根`LICENSE`及实际打包组件的LICENSE/NOTICE | 随对应发布内容保留，不作为无关文档删除 | 按许可要求随包附带 |
| 实际生产配置和秘密 | 由现有模型配置提取必要字段，并按目标环境重新生成 | 模板随包，实际秘密单独受限配置；不能直接同步整个configs目录 | 后台受限配置 |

源码文件按目录盘点约4.1MB；当前完整前端成品为101文件、约17.3MB。它们是现状体积，不是最终最小包大小或内存占用。精简重点还包括大型历史输出、环境、缓存与无关依赖。

前端默认在本地构建，服务器接收成品，因此不必上传`web/rtl-demo/src/`、`node_modules/`或安装前端构建工具。若日后改为服务器构建，源码和构建锁文件才进入单独的构建材料清单。

## 2. 默认不上传

| 内容 | 排除原因及例外 |
| --- | --- |
| `specs/`、项目README、设计讨论、研究和验收日志 | 开发过程资料，不参与线上运行；可另交付一份简明运维说明 |
| `.agents/`、`.specify/`、编辑器和本机开发工具目录 | 本地开发工作流，不是网页或Agent运行依赖；服务账户所需工具配置另外准备 |
| `.git/`及本机修改历史 | 不随运行包迁移；发布记录使用单独版本标识。若运行器要求版本控制工作区，在服务器为该运行初始化，不复制开发仓库历史 |
| `tests/`、浏览器安装缓存、测试截图、覆盖率与测试报告 | 留在构建/验收环境；发布门禁通过结果可写入不含秘密的清单 |
| `.venv-web/`、其他venv/Conda环境、`node_modules/` | 含本机路径和平台依赖，目标机重新安装 |
| 整个`rtl_outputs/`及全部`.zerorepo/` | 含大量历史候选、私有工具会话及无关输出；仅按引用导出四例必要证据和契约 |
| 整个`.rtl-demo/` | 混有本机数据库、消息、会话签名密钥、实时任务、进程记录、预检缓存和诊断；禁止整体复制 |
| `langfuse_local/`、`Accurate_Records_gpt5.6/`、其他实验记录与模型缓存 | 不属于当前运行包；不能因为目录存在就启用另一套监控或模型运行环境 |
| 全部`rtl_dataset/`或整个RealBench | 首版只部署四例实际输入和验证依赖，不上传无关案例 |
| `configs/zerorepo_config.yaml`、`configs/rtl_demo.local.yaml`、本机`.env*`的直接镜像 | 可能含实际秘密、开发路径及本地服务地址；以脱敏模板和生产私有配置分别替代 |
| 本机编译器输出、`obj_dir/`、`.pyc`、`__pycache__/`及`rtl_langs.so`的直接拷贝 | 不能据此假设目标平台可运行；必要本地库在目标兼容环境重建并校验 |
| 本机Codex认证、工具会话及`~/.codex`整体目录 | 为服务器服务账户单独准备合法认证和指定profile，不搬运其他账户的身份与对话历史 |

不能直接照搬gitignore作为发布清单：被忽略的`.vcd`、部分`.zerorepo`契约和构建好的`dist`恰好可能是部署必需品；反过来，版本库中存在的文件也不一定需要上传。

当前网页入口使用`zerorepo.rtl_web.cli`与worker，不通过根`main.py`启动。若计划额外保留原命令行运维入口，再把`main.py`及其对应依赖加入清单，不据此强行安装原仓库全部功能。

## 3. 四例规格与后台数据初始化

必须保留的规格：

| case_id | 仓库路径 |
| --- | --- |
| e203 | `rtl_dataset/e203_exu_alu_hard/e203_exu_alu_system.md` |
| aes_cipher_system_hard | `rtl_dataset/aes_cipher_hard/aes_cipher_system_hard.md` |
| aes_inv_cipher_top_system | `rtl_dataset/aes_inv_cipher_system/aes_inv_cipher_top_system.md` |
| sdc_controller_system | `rtl_dataset/sdc_controller_hard/sdc_controller_system.md` |

后端需要的不只是前端`cases/*.json`。问答依据和真实验证还要访问登记的bundle、run、version、artifact以及对应文件；快照和artifact均有摘要校验，原始VCD由后台解析。

建议在构建端从已审查的四个活跃bundle形成私有初始化数据，按引用闭包包含必需历史run、版本及父子关系、模块源文件、规格/规划、报告、原始VCD、波形索引/分片和来源审查记录。原始VCD与参考设计只存后台，不进入公开目录。公开波形继续使用已导出的白名单信号数据。

**当前缺口**：现有CLI有`import-case`、`prepare-cases`及静态导出，没有独立的可移植后台初始化导入/导出命令。该功能需在后续计划中实现并验证，不能把复制本机整个数据库当作已经解决。

初始化必须满足：

- 新建服务器自己的数据库与会话签名秘密，只导入所需历史记录；无本地聊天、私有实时run、待执行operation、heartbeat、PID、旧预检缓存或本机登录信息。
- 记录与artifact/snapshot文件一并迁移，维护ID、相对存储键、内容摘要和版本绑定，不能只传JSON或只传数据库。
- 历史修复所需stage1契约单独迁移并核对摘要。AES加密案例目前缺少完整历史契约，此限制如实保留，不填造接口。
- 生产数据目录独立于代码版本和静态目录；后续升级仅登记新证据，不覆盖现有会话、运行、验证结果或重建会话密钥。
- 若暂沿用服务器原始历史导入方式，需另列完整输入白名单；E203导入还读取候选journal、指定candidate、accepted baseline和final结果，不能仅传merged。本规格优先把这类历史解析留在构建端。

## 4. RealBench最小验证材料范围

以下路径相对`oracle_root`；验证目录内需保留脚本、TB及实际依赖文件，参考目录内需保留被验证器使用的刺激、参考模块和头文件。最终逐文件清单仍须由脚本依赖与目标机实跑确认。

| 案例 | 验证脚本目录 | 参考材料目录 |
| --- | --- | --- |
| E203 | `system_task/e203_exu_alu_hard/verify_test/` | `e203_hbirdv2/e203_exu_alu/verification/` |
| AES加密 | `system_task/aes_cipher_hard/verify_test/` | `system/aes_cipher_top/` |
| AES解密 | `system_task/aes_inv_cipher_top_hard/verify_test/` | `system/aes_inv_cipher_top/` |
| SDC | `system_task/sdc_controller_hard/verify_test/` | `sdc/sdc_controller/verification/` |

当前四个验证脚本使用标准库调用外部工具，没有发现需要复制整个RealBench Python环境的依据。但它们依赖完整HDL材料、支持相应参数的Verilator、C++编译器和make；仅安装Python包不能仿真。

已发现需要处理的迁移问题：

1. AES两例脚本写死`REALBENCH_ROOT=/home/mokita/RealBench`。现有包装器未统一覆盖该值，单改Web的`oracle_root`无法保证生效。
2. 四例脚本还带本机Conda工具路径。需要核对真正生效的PATH与工具版本，不能只检查`which verilator`。
3. 四例Verilator参数均包含`-j 4`；全局一个worker不等于编译只有一个进程。在2核/约2GB机器上需为编译并发单独做预算，必要时采用受审查的低并发执行设置。
4. 路径及资源参数适配必须与原始受信脚本、TB、参考材料摘要和实际执行参数关联记录；不能改刺激、比较表达式或错误屏蔽来让部署验收通过。

## 5. 服务器环境与配置

### 运行环境按能力核对

| 层次 | 准备内容 | 验证方式 |
| --- | --- | --- |
| 解释器 | 独立于系统默认环境及现有CAD服务的新环境；以已测试的Agent解释器版本为基线 | 解释器绝对路径、模块导入及真实任务 |
| Web层 | 当前Web依赖及其兼容锁定版本；生产包区分测试工具 | API、会话、波形、事件与访问边界验证 |
| 真实问答 | 现有LLMClient及当前选定provider所需SDK/依赖 | 目标机通过正式域名连续真实问答 |
| 独立验证 | 运行适配层、参考材料、Verilator、C++编译器、make和可写临时空间 | 四例各自真实复验、报告与波形归档 |
| 生成/修复 | Planner、当前Debug后端、指定Codex profile/认证、必需KG及解析器依赖 | 真实生成和失败版本修复，不能仅凭import或登录状态判定 |
| 知识图谱 | 当前所需Neo4j连接、账号、分区及Verilog语法解析资源 | 真实连接并解析/查询当前RTL；不能只有端口连通 |

默认系统Python实测为3.6.8，不适合当前代码；服务器另有供其他服务使用的3.12解释器，不能据此复用CAD环境。当前本地Agent已测Python为3.13.11，Web与Agent仍按已验证边界准备，可分别建环境并锁定实际依赖。

不能直接执行根`requirements.txt`作为“生产安装完成”：它同时包含多provider、ML、向量检索、开发工具及旧功能依赖；当前实际环境也与声明不同。例如本机OpenAI SDK为1.109.1，而根清单要求>=2.14.0。需要在隔离环境解析和实测本路径依赖，再形成生产锁文件；没有路径证明的torch/模型权重等不自动安装，也不据此删掉实际必需的KG功能。

知识图谱解析器尤其需要验证：本机tree-sitter为0.25.2，代码在缺少`rtl_langs.so`时调用`Language.build_library`，加载已有库时另有兼容分支。根清单与KG依赖声明又不同。因此“复制现有环境”或“删掉.so后直接安装最新库”都不能当成正确方案。应保留`zerorepo/rtl_impl/rtl_kg/third_party/tree-sitter-verilog/`的必要C源码、头文件及许可，使用已验证的构建路径产出目标兼容库，配置`RTL_TS_LANG_SO`等实际路径，并测试真实解析。源码目录只读时，构建产物应放入允许的构建/缓存目录。

### 生产配置逐项迁移

| 配置项 | 迁移要求 |
| --- | --- |
| repo_root / runtime.python | 指向服务器实际部署目录与解释器，不能保留开发机绝对路径 |
| data_root / 临时目录 / 编译及解析缓存 | 独立持久数据与受限可写目录；明确磁盘、清理及运行预算 |
| spec、source、bundle引用 | 对应四例输入、初始化记录和历史契约；目前`source_output`仍用于历史修复，不能随意删除 |
| oracle_root / toolchain_bin | 对应私有验证资源和真实工具；同时处理验证脚本内部路径 |
| development / allowed_origins | 生产关闭开发访问放行，来源匹配正式design域名 |
| 监听及站点转发 | 单机仅通过现有受保护入口访问后台，不复用28989；具体端口和路径在plan确认 |
| 模型配置 | 沿用当前provider、model及已授权端点；实际密钥单独受限提供，不能直接同步本机配置原件 |
| Codex后端 | 安装现有后端所需CLI，准备服务账户自己的合法认证和指定profile；不因配置缺失换后端 |
| KG连接 | 核对服务器上的实际地址、凭据和分区；本机localhost不表示服务器有同一服务 |
| 会话及入口秘密 | 在服务器独立配置/生成；不复制本地session.key或复用其他站点的秘密 |
| 服务启动环境 | 管理服务、API、worker及子进程使用一致配置，不依赖交互SSH终端的Conda激活、PATH或临时export |

## 6. 后续计划必须落实的交付物

- 文件白名单和排除清单：每项有来源、用途、可见范围、摘要及体积；私有配置实际值不写入发布清单。
- 前端、后台源码、私有四例初始化材料、验证材料及运维安装材料分别打包，不能把私有材料放进静态站点。
- 可移植后台初始化的导入/导出及升级保护；历史契约路径映射与来源校验。
- Web和Agent依赖锁定结果、目标机解释器/编译器/解析器的兼容性证明，以及必要的服务账户认证和知识服务配置。
- 路径及编译并发适配的审查记录，四例目标机真实验证，以及生成/修复依赖的完整检查。
- 从干净部署目录冷启动的验收；证明无需开发机仓库、虚拟环境、私有会话和旧缓存也能运行。

这些准备不会改变原有功能范围；问答或历史展示的精简环境不能被当作完整生成、验证和修复环境已经部署。
