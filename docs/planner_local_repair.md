# 规划执行与恢复

Stage1—Stage4 保留责任与耦合感知的方法链：规格来源 → RU → 模块划分 → 行为义务与结构块 → 局部任务 → 门控。执行层参考本地 pi 的请求与执行循环分离、错误结果反馈、会话持久化方式；仍为 Python，不启动 Node/RPC 或 pi-durable。

## 权威数据

- Stage1：事实及顶层接口保持现有抽取方式。
- Stage2：三种架构候选、双轮排序、分歧裁定保持原机制。模型在责任草稿中选择 `EV_...`，程序展开完整 `SourceEvidence` 并严格核验原文。
- Stage3：模型返回 `ModuleSkeletonDraft`，包含框架、结构块、行为义务及可选来源绑定请求。程序组装模块身份、占位符、状态对象、继承契约、完整来源和 Overlay。`skeleton.json` 为权威数据；五章节 Markdown 由程序渲染，不参与规划解析和缓存内容指纹。
- Stage4：一块一任务，稳定拓扑排序，无模型调用。描述来自 purpose，简短 constraints 为空，完整义务及状态契约保留。规格块携带证据映射，选择一个证据时保留它对应的全部块。

声明及元信息块只能提供支持，不能单独满足功能责任。每项任务都必须有明确的义务关系。实例块只实现本模块的集成义务；实例任务额外取得选中边界端点的来源，不能据此重复归属子模块责任。运行时反馈不转换为生成依赖。

## 单一节点循环

`PlanningSession` 负责：准备上下文 → 请求 → 结构校验 → 领域校验 → 原子保存候选、问题和范围 → 修正或提交。

Stage1 和架构选择返回其结构化对象；Stage2 责任修复按 RU/状态 ID 替换完整实体；Stage3 按义务/结构块 ID 替换实体。缺少新义务时允许在指定 RU 范围内新增。相关实体一起合并后执行全量领域检查，不修改范围外的实体。

Stage2 的领域错误定位到实际包含错误字段的实体。例如，状态缺少 `commit` 访问时，修复目标是 `responsibilities[拥有者RU].state_accesses`，反馈同时给出所需的状态 ID 和角色；状态表保持锁定。错误消息中的状态、依赖目标等引用不额外授权修改这些实体。恢复时重新校验候选并计算修复范围；范围改变后丢弃旧范围产生的过期拒绝反馈。连续无进展退出时，同时报告候选校验错误和修复响应被拒绝的原因。

Stage2、Stage3 的提示词证据目录将重复的文件路径和章节路径提取为共享字典；每项仍保留原有 EV ID、全部原文及行区间，可无损展开为完整目录。权威本地注册表不改变，模型只选择 EV ID。责任抽取中的架构事实通过已有事实 ID 引用，避免重复发送同一条事实；不通过截断原文来满足请求大小限制。

Stage3 的模块合同提示视图保留接口、时钟/复位及责任来源等合同字段，派生事实正文改为完整事实 ID 列表及原始合同内容指纹；完整原文由 EV 目录提供，完整 RU、状态和边界另行显式输入，权威合同不修改。指纹覆盖未输入模型的事实正文，事实内容改变仍会使节点失效。这也避免顶层继承全部子模块事实，或首次运行的内存合同比落盘视图携带更多原文锚点时，重复输入同一规格。Stage4 声明证据按原文件收集全部相关完整端口表，不以单个最高匹配片段替代整个接口；新注册的精确表格证据继续保存在统一注册表。接口映射策略具有独立指纹，调整映射时仅重建 Stage4 派生产物。

Stage3 修复请求继续保留完整候选、EV 原文目录、模块 RU、状态及接口约束、边界合同和错误定位；模块合同中的派生事实正文改为事实 ID，避免与原文重复后挤占候选空间。检查点指纹始终绑定未缩减的完整输入，因此事实或上游内容改变仍会失效，预算超限后也可恢复同一候选并继续实体修复。

示例修正响应：

```json
{"behavioral_obligations":[{
  "obligation_id":"OB_RESET",
  "parent_responsibility_id":"RU_CONTROL",
  "behavior_kind":"reset",
  "required_effect":"按规格清除控制状态",
  "source_evidence_ids":["EV_<已提供的标识>"],
  "state_accesses":[{"state_id":"ST_CONTROL","role":"reset"}],
  "implementation_block_id":"B3"
}]}
```

这是一项完整实体，不是字段补丁。允许省略的字段遵循同一草稿 schema 的默认值；未指定的触发、守卫和时序保留为 unspecified。模型不生成来源原文、行号、哈希及已确定的继承契约。Stage3 主流程没有 Markdown 字段定位、围栏修复或全文文档补丁。

结构无效、越权或重复实体响应不能覆盖当前候选。两个连续响应没有改变候选及其错误集合时，节点保存 `needs_repair` 并结束本轮；这不表示规划成功。鉴权、配置及节点时间/API 预算耗尽明确失败。原有 Stage3 固定三次内容尝试已从主流程移除。

## 请求与会话持久化

`RequestExecutor` 是唯一传输监督层；Stage5 复用其底层，生成和 debug 策略保持原机制。工作台只订阅规划事件，观察器错误不改变执行结果。

`plan/state/execution/` 保存带内容校验的节点检查点。每次请求前持久化候选、问题、允许修改的实体及累计消耗；响应先保存再解析，重启时可覆盖“已收到完整响应、尚未提交候选”的中断窗口。旧连接结果不会接入新进程。

默认节点预算为本轮 1800 秒、10 次实际 API 尝试；传输重试也计入。请求时间、首正文、空闲和重试规则仍由 request_policy 管理，不能绕过节点总预算。必要上下文过大时记录实际大小并停止，不截断强制来源。

Stage1 按最多五个文件、约 1.8 万原文字符组织事实抽取请求。长文档优先在段落或章节边界切分，必要时沿完整行切分，分段不丢弃或改写输入文本；不可拆分的超长行单独处理。每段携带原文件位置、章节上下文和内容指纹，不生成新的规格文件。分段批次的完成标识绑定实际内容及区间，已完成批次无需重抽；后续分段请求只带模块名称等必要上下文，完整事实表由程序持久化并合并，不在每次请求中重复发送。此规则用于避免单个长规格反复耗尽模型的输出长度。

`--resume` 重新核对规格、模型配置、阶段模板、上游内容和检查点版本，重新校验保存的候选。显式续跑为未完成节点分配本轮预算，累计统计保留。`--force-rebuild` 不读取这些缓存。

来源补充只接受已核验 EV ID，且每个 RU 每次节点执行最多一次。程序仅追加关联、重验责任表、刷新模块切片；其他责任字段及已有义务不变。受影响的已完成骨架重新校验，派生上下文重新构建，下游任务输入指纹更新。当前候选随合法输入更新持久化到新指纹，可在下一请求超时后恢复。

## 门控及缓存

门控读取 JSON 正文，核验来源、责任归属、约束、状态身份与提交块、义务与块映射、完整规格文本及任务映射。使用同一确定性任务组装器验证恢复结果。门控失败保存定位信息，不调用代码生成。它不证明 RTL 功能正确性。

Stage5、Stage6、KG 投影及离线生成恢复使用骨架 JSON；Markdown 缺失或被编辑时按 JSON 重建。Stage5 缓存绑定完整骨架 JSON、当前任务、义务和相关来源。

策略 `planning_harness_v2` 与检查点 `planning_node_v2` 首次升级使旧 Stage1—Stage4 规划失效，不导入旧失败草稿。目录布局仍为 plan/generate/debug，运行边界仍为 `--plan`、`--generate` 和完整流程。历史 Markdown 解析工具只供独立历史格式检查，不是主流程或恢复模式。

## 诊断和留存

`plan/metrics.json` 汇总逐请求 JSONL。没有服务端 usage 的调用保留未知标识，不用字符数冒充 token，也不估算货币费用。失败与重试记录参与统计。

compact 保留恢复所需候选及最近失败诊断；权威产物落盘后才清理成功临时记录。full 额外保存完整请求、响应和过程诊断。两种模式的校验及恢复判定相同。Stage5 的代码/契约局部修复与不可变版本、Stage6 的合并和修复发布规则保持原有实现。
