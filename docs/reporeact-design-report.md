# RepoReAct Runner 设计报告

## 一、定位与核心思路

RepoReAct Runner 是一个**仓库级 RTL 自动修复引擎**。它的核心任务是在仿真失败后，像一名有方法论的调试工程师一样，自主完成从信息收集、根因定位、到精准修复的完整闭环。

整个设计围绕一个核心命题展开：**如何让 LLM 在一个有限上下文的条件下，系统性地完成复杂的硬件调试任务？**

答案分为三个层面：
1. **认知框架** —— 用 Prompt 为 LLM 建立结构化的推理思维
2. **执行纪律** —— 用工具层的硬约束确保关键步骤不被跳过
3. **记忆管理** —— 用多层次上下文系统在有限窗口中维持修复状态

## 二、ReAct Loop 设计

### 2.1 核心结构：双层循环

系统采用**外部监督 + 内部自治**的双层循环架构。

**外层循环**由 Runner 控制，每轮执行以下步骤：
1. 检查终止条件（仿真通过 / 达到最大步数）
2. 判断是否需要压缩上下文
3. 将当前状态摘要注入给 LLM
4. 等待 LLM 完成一轮或多轮思考-行动-观察

**内层循环**由 LLM 在每轮中自主驱动，它根据获得的状态信息，自行决定调用哪些工具、收集多少证据、何时动手修复。内层有独立的最大迭代次数限制，防止单轮陷入无限循环。

这种双层设计的好处是**分工明确**：外层负责资源控制（上下文预算、行动预算、终止判断），内层负责推理决策。

### 2.2 步数与行动数：两套独立的预算系统

系统维护两个独立的计数器：

- **循环步数**：外层循环的轮次。每向 LLM 发送一次状态更新，计一步。
- **行动次数**：LLM 实际执行的写操作次数（应用补丁、替换代码块、记录纠正）。

两者不同步是故意的——LLM 可以在一步内执行零次行动（纯观察被预算拦截），也可以在一步内执行多次行动（内层 ReAct 迭代多次）。行动预算才是真正的硬限制，步数预算更像是一个安全兜底。

### 2.3 终止条件设计

循环有三重终止条件，在多个时机点检查：

1. **仿真通过**：当前模块的所有 mismatch 归零。优先级最高。
2. **行动预算耗尽**：写操作次数达到上限。意味着系统在现有条件下已无法继续改进。
3. **循环步数耗尽**：外层迭代轮次达到上限。安全兜底，防止无限循环。

同一个条件在循环开头、上下文压缩后、LLM 返回后三个位置重复检查，确保在任何情况下都能及时退出。

### 2.4 初始回合：免费观察机制

第一条消息的特殊之处在于，它不计入行动预算。LLM 在这个"第零步"可以自由地进行信息收集——读规格、读 RTL、查知识图谱、跑仿真——而不用担心消耗后续的修复预算。这是一个**刻意设计的暖身阶段**，让 LLM 在动手之前先建立对问题的完整认知。

## 三、上下文管理

### 3.1 三层架构

系统维护三层上下文，各有不同的职责和生命周期：

**第一层：原始对话历史。** 这是 LLM 实际"看到"的上下文，包含所有用户消息、助手回复、工具调用和工具返回结果。它线性累积，是 LLM 推理的直接依据。

**第二层：结构化记忆快照。** 这是系统从对话历史中提炼出的结构化 JSON，包含仿真状态、修复账本、受保护的不变量、禁止尝试的方向、下一个修复目标、高耦合模块等信息。它是上下文压缩后唯一幸存的信息载体。

**第三层：磁盘日志。** 完整的审计轨迹，包括所有对话记录、每一次补丁尝试的详细前后对比、文件快照等。LLM 不直接消费这层信息（除非通过工具读取），它主要用于事后分析和系统回放。

### 3.2 上下文压缩：硬重置机制

当满足以下任一条件时，触发上下文压缩：
- 自上次压缩以来执行了 2 次或以上的写操作
- 自上次压缩以来工具返回的文本累计超过 16,000 字符

压缩的执行方式是**硬重置**：清空 LLM 的全部对话历史，只保留一份结构化的记忆摘要 JSON 作为新的起点。

这是一个关键技术决策。它承认了一个现实：在复杂的多轮修复中，对话历史必然超出 LLM 的上下文窗口。与其让 LLM 在超长上下文中遗忘早期关键信息，不如主动压缩，用结构化摘要替代原始对话。

**代价**：所有中间的推理过程、工具调用的具体返回内容、LLM 当时的思考细节——全部永久丢失。压缩后 LLM 唯一的知识来源是那个结构化摘要。如果摘要遗漏了某个关键发现，LLM 需要重新调用工具来恢复。

### 3.3 记忆摘要：压缩后的唯一信息载体

记忆摘要是整个上下文管理系统中最关键的数据结构。它在压缩时承载了全部幸存信息，也在每一步循环中作为状态更新发送给 LLM。

摘要包含以下核心信息：

| 信息类别 | 内容 | 来源 |
|---------|------|------|
| 仿真状态 | 是否通过、mismatch 数量、首次失败时间 | 实时仿真结果 |
| Trace 摘要 | 失败时间、根因信号、可疑代码块 | 自动化 trace 分析 |
| 分歧摘要 | DUT 与参考模型的第一分歧点、采样模式 | first_divergence 分析 |
| 修复账本 | 最近 10 次尝试：做了什么、效果如何、经验教训 | 从补丁日志反向推导 |
| 受保护项 | 之前成功修复中建立的、不可破坏的行为约束 | 从成功补丁中自动提取 |
| 禁止方向 | 已验证会退化的修复思路，不要重复尝试 | 从失败补丁中自动提取 |
| 当前目标 | 下一个应该修复的信号、时间点、症状描述 | 分歧分析 + 受保护项结合 |
| 高耦合块 | 涉及 6 个以上信号的代码块，编辑时需要特殊保护 | 从补丁日志中统计 |

**关键设计**：摘要中的信息（受保护项、禁止方向、高耦合块）不是人工标注的，而是从补丁日志中**自动推导**的。系统通过分析每次补丁的效果（通过/改善/退化/失败），自动提取出"哪些行为必须保护"和"哪些方向不要重复"。这是一个自动化的经验学习闭环。

### 3.4 观察预算：上下文门控

除了主动压缩，系统还通过**观察预算**来控制上下文的增长速度。

LLM 的每次工具调用被分为两类：**只读调用**（观察类，如读文件、查波形、搜索代码）和**写调用**（动作类，如应用补丁、记录纠正）。

规则很简单：每做一次观察，观察计数加一；每做一次动作，观察计数归零。当观察计数超过上限（默认 16 次），所有观察类工具被直接拒绝，系统返回"观察预算耗尽"的错误，并附带当前的结构化记忆摘要，强制 LLM 在现有证据基础上执行修复动作。

这是一个**渐进收紧**的压力设计：
- 预算充裕时，LLM 看到温和的提示"观察可以，但要有针对性"
- 预算接近上限时，LLM 看到强烈的催促"行动压力：你该动手了"
- 预算耗尽时，工具直接拒绝服务，LLM 别无选择

### 3.5 三种消息的叙事分工

系统在三个不同的时间点向 LLM 发送三种不同类型的消息，它们共同构成一个完整的修复叙事：

**初始消息**（第零步）：这是案件简报。包含模块名称、修复模式、RTL 路径、规格书摘要、接口契约摘要、仿真失败日志、自动化 trace 分析结果、已知的历史纠正记录、以及初始的记忆状态。它告诉 LLM："这是案发现场，这是所有已知证据，请开始调查。"

**继续消息**（每步循环）：这是进展报告。包含最新的记忆摘要（仿真状态、修复账本、受保护项、禁止方向、当前目标）和观察预算倒计时。它告诉 LLM："这是当前状态，这是你还剩的观察次数，请在预算内完成下一步。"

**压缩消息**（上下文重置时）：这是失忆后的备忘录。只有一份浓缩的结构化记忆摘要和六条精简的行为规则。它告诉 LLM："你失去了之前的对话记忆，这份 JSON 是你全部的知识备份，请据此继续工作。"

## 四、工具设计

### 4.1 三层分类

系统提供 12 个工具，按职责分为三层：

**观察层（8 个工具）**：用于信息收集，不产生任何副作用。
- 代码阅读类：读取仓库结构、文件内容、行范围、阶段产物
- 搜索类：在 RTL/测试平台/规格中正则搜索
- 知识图谱类：查询模块接口、实例层次、信号连接、信号驱动
- 规格类：读取原始规格文档或按 ID/查询检索规格条目
- 波形类：列出 VCD 信号、在特定时间窗口采样信号值
- 检查类：运行 Lint、模块仿真、Trace 分析、第一分歧点分析

**动作层（2 个工具）**：用于修改代码，每次执行都会触发验证流水线。
- 行级补丁：替换指定行范围的代码，支持单次提交多个协调修改
- 块级替换：替换整个 always/assign 代码块，适用于像默认值策略、状态机编码这类语义上不可分割的修改

**元操作层（2 个工具）**：不修改代码，但影响修复流程。
- 记录纠正：当根因不在 RTL 而在上游规划时，记录纠正覆盖层
- 读取记忆：访问修复状态的各类视图

### 4.2 工具的三层处理架构

每个工具调用经过三层处理，实现了关注点的清晰分离：

**第一层 —— 横切检查：** 进行预算验证、上下文门控。如果观察预算已耗尽，直接在此拦截，返回结构化记忆摘要而非错误信息。

**第二层 —— 业务逻辑：** 执行工具的实际功能。包括路径安全检查、文件读取、知识图谱查询、仿真运行等。

**第三层 —— 横切记录：** 将工具调用和结果写入完整的审计日志（用于事后分析和回放），更新上下文压缩的字符计数，更新观察预算的计数器。

### 4.3 补丁验证流水线

应用补丁不是简单的文本替换，而是一个完整的**验证-回滚**流水线：

1. **前置校验**：检查补丁目标的合法性（只允许编辑当前模块的 RTL 源代码）、范围有效性（行号不越界）、内容安全性（不涉及被保护的路径如规格文件/测试平台/知识库）

2. **证据门禁**（详见 4.4 节）：确保 LLM 在修改代码前已经收集了足够的证据

3. **保护检查**：如果补丁可能影响之前成功修复中建立的不变量，系统要求 LLM 显式声明它已经检查过这些不变量，并提供了保护计划。否则拒绝执行。

4. **文件快照**：在修改前后各创建一份文件副本，用于事后比对

5. **原子应用**：按行号逆序应用所有修改（保证行号不会因前置修改而漂移）

6. **自动验证**：
   - 第一关：Lint 检查。通不过→自动回滚到修改前的状态
   - 第二关：如果是语法修复模式，Lint 通过即为成功
   - 第三关：运行模块仿真。mismatch 数量退化→自动回滚。首次失败时间提前→自动回滚

7. **效果分级判定**：不是简单的通过/失败二分，而是六级分类
   - **通过**：仿真通过，mismatch 归零。终极目标。
   - **改善**：mismatch 数量减少，或首次失败时间推后。虽然是局部改善，但补丁予以保留。
   - **中性**：仿真结果没有统计学意义上的变化。可以保留，但连续三次中性的补丁会被自动回滚（防止 LLM 做无意义的微调循环）。
   - **退化**：mismatch 增加或失败时间提前。自动回滚。
   - **语法失败**：Lint 不通过。自动回滚。
   - **拒绝**：在前置检查阶段就被拦截，根本没有执行。

### 4.4 证据门禁系统

这是整个工具设计中最关键的安全机制。在补丁工具真正执行之前，系统强制要求 LLM 必须满足五个前置条件：

1. **已阅读当前 RTL 源代码** —— 不能对着旧代码或凭空猜测做修改
2. **已查看 Trace 或仿真结果** —— 必须基于实际的错误证据，不能凭想象
3. **已查看测试平台/规格/知识图谱中至少一种** —— 必须理解设计的预期行为
4. **（功能修复模式）已调用第一分歧点分析** —— 必须知道 DUT 和参考模型的确切差异
5. **（功能修复模式）已阅读规格或阶段产物** —— 必须基于设计意图做修改，不能只看波形

这五道门禁的核心思路是：**不依赖 LLM 自觉遵守行为规范，而是在基础设施层强制执行**。系统提示中写"补丁前要收集证据"是软约束（LLM 可以选择忽略），但工具层的这五道门禁是硬约束（LLM 无法绕过）。

### 4.5 从补丁日志到因果记忆：自动化的经验学习

每次补丁尝试（无论成功还是失败）都被持久化到补丁日志中，包含完整的修改前后对比、效果分类和教训总结。

系统通过分析这些日志，自动构建出 LLM 在下一轮循环中可用的因果记忆：

- **修复账本**：按时间倒序展示最近的所有尝试，让 LLM 知道"我试过什么"
- **受保护的不变量**：从成功和改善的补丁中提取，自动生成保护规则。例如，如果之前的补丁修复了 ack_out 信号的行为，系统会自动生成"不要破坏 ack_out 在 SETUP 状态下的保持行为"这样的保护规则
- **禁止尝试的方向**：从退化和语法失败的补丁中提取。例如，如果替换某个代码块导致了退化，系统会自动记录"不要再次替换该块，除非有新的区分性证据"
- **高耦合模块**：通过统计补丁涉及的信号数量，自动识别出"牵一发而动全身"的模块，标记为高耦合，要求编辑时提供额外的保护计划

这套机制的强大之处在于：它不是静态的规则库，而是**随修复过程动态演化**的经验体系。LLM 在每一步都能看到自己（或之前的修复会话）积累的经验和教训。

### 4.6 自我感知能力

通过"读取记忆"工具，LLM 可以主动查询自己的修复状态。这不是被动接受状态注入，而是**主动检索**。

LLM 可以在任何时候查询：
- 完整的结构化状态快照
- 修复历史（最近尝试了什么）
- 受保护项（哪些已有改善不能破坏）
- 禁止方向（哪些思路已验证失败）
- 有希望的方向（哪些思路已验证有效）
- 当前目标（下一步应该集中修哪个信号）

这种自我感知能力使得 LLM 可以在新一轮开始前做一次"记忆检索"，对比当前状态和历史经验，避免重蹈覆辙。

## 五、认知框架：Prompt 设计原理

### 5.1 五阶段思维流水线

System Prompt 将修复过程组织为一条强制的认知流水线，每阶段对应一类明确的行为：

| 阶段 | 目标 | 核心约束 |
|------|------|---------|
| 信息收集 | 建立对问题的完整认知 | 跨模块问题查知识图谱，根因不明查波形，功能模式必须先跑分歧分析 |
| 因果诊断 | 将模糊的"仿真失败"转化为可操作的诊断结论 | 每次行动前必须填写诊断 JSON，明确失败类型、根因信号、参考值与实际值的差异 |
| 记忆检索 | 不重复过去的错误 | 检查已有的受保护项和禁止方向，有相似失败记录时必须有新证据才能重试 |
| 范围决策 | 选择与根因精准匹配的修复粒度 | 一行、多行协调修改、整块替换都可以，唯一标准是"直接对应根因" |
| 执行 | 在约束内完成修复 | 只能通过指定工具修改代码，规划层问题走纠正记录而不是直接改 RTL |

### 5.2 诊断 JSON：强制 LLM 结构化思考

嵌入在 System Prompt 中的诊断 JSON 模板是整个认知框架的核心。它在每个行动步骤前强制 LLM 回答 10 个问题：

1. **失败类型** —— 迫使 LLM 将模糊的"仿真失败"映射到具体的 bug 类别
2. **怀疑的模块/文件/信号** —— 迫使 LLM 缩小排查范围
3. **根因信号** —— 迫使 LLM 找出最早的出错信号
4. **第一分歧时间** —— 迫使 LLM 做精确的时间定位
5. **参考值 vs 实际值** —— 迫使 LLM 量化差距
6. **偏差分类** —— 迫使 LLM 区分时序错误和逻辑错误
7. **证据清单** —— 迫使 LLM 为其诊断提供依据，防止幻觉
8. **受保护项检查** —— 迫使 LLM 关注不能破坏的已有改善
9. **保护计划** —— 迫使 LLM 主动思考如何保护已有行为
10. **下一步行动决策** —— 迫使 LLM 做出明确的行动选择

这个 JSON 模板本质上是一个**调试工程师的思维清单**。它不是在"帮助 LLM 更好地回答"，而是在"规定 LLM 必须以什么方式思考"。

### 5.3 领域知识注入

Prompt 中包含了三条关键的领域知识——它们是 RTL 调试专家才知道的"经验法则"：

**规则一：区分测试平台指标和 RTL 信号。** 仿真日志中大量的 `errors_*`、`errortime_*`、`tb_match*` 信号是测试平台层面的统计指标，不是根因级别的 RTL 信号。LLM 如果不理解这一点，会在错误的信号上浪费大量时间。

**规则二：边缘采样不匹配的特殊处理。** 当 DUT 和参考模型的稳定值一致，但在测试平台采样边缘不一致时，问题几乎可以确定是阻塞/非阻塞赋值语义或 `#1` 延迟的差异。这条规则给了 LLM 一个诊断捷径。

**规则三：编辑范围以一致性为准，不以最小化为准。** LLM 通常有"越少改动越好"的偏见。这在软件工程中通常是正确的，但在 RTL 修复中，如果根因需要一次语义一致的重构（比如重写一个 always 块的默认值策略），分多次小改反而会引入新 bug。这条规则明确告诉 LLM：保持语义一致性比压缩改动行数更重要。

### 5.4 权威来源声明

初始消息中包含一句明确的声明：**"测试平台和原始模块规格是本次修复会话的权威来源。"**

这句话建立了一个不可协商的层级关系：规格 > 阶段产物（规划假设） > RTL > LLM 的猜测。如果 RTL 代码和规格文档有冲突，改 RTL。如果阶段产物和规格有冲突，记录纠正。LLM 不应该质疑规格的正确性。

### 5.5 修复模式的分叉

系统支持两种修复模式，产生完全不同的行为路径：

**语法修复模式：** Lint 通过即为成功条件。LLM 被引导关注编译错误、接口定义、宏缺失、声明缺陷和 Verilator 诊断信息。不需要仿真验证，不需要分歧分析。

**功能修复模式：** 仿真通过（mismatch 归零）才是成功。LLM 被要求先建立语义意图（读规格），再定位事实（trace/VCD），再做因果推理，最后执行。证据门禁的五道关卡在功能模式下全部生效。

这确保了在语法修复中不会进行过度复杂的分析，而在功能修复中不会跳过关键的证据收集步骤。

## 六、设计原则总结

### 6.1 信任但不依赖

系统信任 LLM 的推理能力（通过复杂的 System Prompt 和诊断 JSON 框架引导其思考），但不依赖 LLM 的自觉性（通过工具层的证据门禁和观察预算硬性约束其行为）。

### 6.2 信息密度分层

不是给 LLM 越多的上下文越好，而是根据信息的半衰期做分层处理。原始对话（半衰期短）→ 在压缩时丢弃。结构化摘要（半衰期长）→ 在压缩时保留。磁盘日志（半衰期最长）→ 一直保留，LLM 只在需要时通过工具读取。

### 6.3 压力模型渐进收紧

观察预算从"温和提醒"到"强烈催促"到"直接拒绝"，形成渐进的压力曲线。LLM 有充分的机会根据压力调整策略，但最终会被强制行动。

### 6.4 自动化的经验积累

受保护项、禁止方向、高耦合模块——这些"记忆"不是人工标注的，而是从补丁日志中自动导出的。系统在一步步的修复尝试中自己学会了"什么该保护"和"什么不该重复"。

### 6.5 原子操作保证一致性

每一次修改（无论是行级补丁还是块级替换）都是原子操作：应用→验证→回滚（如果需要）作为一个不可分割的整体。外部永远看到一致的状态——要么是修改前的干净版本，要么是验证通过的修改后版本。
