# RepoReAct Runner 设计报告

## 一、定位与核心思路

RepoReAct Runner 是一个**仓库级 RTL 自动修复引擎**。它的核心任务是在仿真失败后，像一名有方法论的调试工程师一样，自主完成从信息收集、根因定位、到精准修复的完整闭环。

整个设计围绕一个核心命题展开：**如何让 LLM 在一个有限上下文的条件下，系统性地完成复杂的硬件调试任务？**

答案分为三个层面：
1. **认知框架** —— 用 Prompt 为 LLM 建立结构化的推理思维
2. **执行纪律** —— 用工具层的硬约束确保关键步骤不被跳过
3. **记忆管理** —— 用多层次上下文系统在有限窗口中维持修复状态

---

## 二、ReAct Loop 设计

### 2.1 核心结构：双层循环

系统采用**外部监督 + 内部自治**的双层循环架构。

**外层循环**由 Runner 控制，每轮执行以下步骤：
1. 检查终止条件（仿真通过 / 达到最大步数）
2. 判断是否需要压缩上下文
3. 将当前状态摘要注入给 LLM
4. 等待 LLM 完成一轮或多轮思考-行动-观察

**内层循环**由 LLM 在每轮中自主驱动，它根据获得的状态信息，自行决定调用哪些工具、收集多少证据、何时动手修复。内层有独立的最大迭代次数限制，防止单轮陷入无限循环。

这种双层设计的好处是**分工明确**：外层负责资源控制（上下文预算、行动预算、终止判断），内层负责推理决策。

### 2.2 步数与行动数：两套独立的预算系统

系统维护两个独立的计数器：

- **循环步数**：外层循环的轮次。每向 LLM 发送一次状态更新，计一步。
- **行动次数**：LLM 实际执行的写操作次数（应用补丁、替换代码块、记录纠正）。

两者不同步是故意的——LLM 可以在一步内执行零次行动（纯观察被预算拦截），也可以在一步内执行多次行动（内层 ReAct 迭代多次）。行动预算才是真正的硬限制，步数预算更像是一个安全兜底。

### 2.3 终止条件设计

循环有三重终止条件，在多个时机点检查：

1. **仿真通过**：当前模块的所有 mismatch 归零。优先级最高。
2. **行动预算耗尽**：写操作次数达到上限。意味着系统在现有条件下已无法继续改进。
3. **循环步数耗尽**：外层迭代轮次达到上限。安全兜底，防止无限循环。

同一个条件在循环开头、上下文压缩后、LLM 返回后三个位置重复检查，确保在任何情况下都能及时退出。

### 2.4 初始回合：免费观察机制

第一条消息的特殊之处在于，它不计入行动预算。LLM 在这个"第零步"可以自由地进行信息收集——读规格、读 RTL、查知识图谱、跑仿真——而不用担心消耗后续的修复预算。这是一个**刻意设计的暖身阶段**，让 LLM 在动手之前先建立对问题的完整认知。

## 三、上下文管理

### 3.1 三层架构

系统维护三层上下文，各有不同的职责和生命周期：

**第一层：原始对话历史。** 这是 LLM 实际"看到"的上下文，包含所有用户消息、助手回复、工具调用和工具返回结果。它线性累积，是 LLM 推理的直接依据。

**第二层：结构化记忆快照。** 这是系统从对话历史中提炼出的结构化 JSON，包含仿真状态、修复账本、受保护的不变量、禁止尝试的方向、下一个修复目标、高耦合模块等信息。它是上下文压缩后唯一幸存的信息载体。

**第三层：磁盘日志。** 完整的审计轨迹，包括所有对话记录、每一次补丁尝试的详细前后对比、文件快照等。LLM 不直接消费这层信息（除非通过工具读取），它主要用于事后分析和系统回放。

### 3.2 上下文压缩：三层渐进式机制

旧的单一阈值压缩策略（"工具字符超过阈值 → 硬重置"）有两个根本问题：太激进时，Agent 刚开始观察就被清空，陷入"观察→压缩→再观察"的死循环；太保守时，Agent 在臃肿的上下文中决策质量急剧下降。

三层压缩的核心思路是**渐进式压缩，根据 Agent 的实际状态动态选择压缩强度**。

**第一层 —— Light Consolidation（轻量刷新）**：不删除任何对话历史，只刷新上下文包（任务框架、时序证据、因果记忆摘要），将最新的修复记录和不变量更新同步给 Agent。触发条件为 8 次只读调用、或 24K 工具返回字符、或一次新的写操作。这一层解决了"数据脏读"问题：Agent 记得自己刚做了什么，但注入的摘要数据还是旧的，Light Consolidation 让两者重新同步。

**第二层 —— Checkpoint Compact（检查点压缩）**：清空全部对话历史，注入一份结构化的状态快照。触发需要两个条件同时满足：Agent 已获取真实的 DUT/ref 差异数据（证明调查足够深入），以及累积了 3 次写操作或 96K 字符（证明上下文确实需要清理）。这意味着在 Agent 形成初步诊断之前，Checkpoint 永远不会触发。快照不仅包含自动计算的摘要（任务框架、时序证据、修复账本），还包含 Agent 主动声明的**工作集**——正在验证哪些假设、已确认哪些波形事实、锁定了哪些代码片段、排除了哪些方向、下一步想改哪里。

**第三层 —— Deep Compact（深度压缩）**：当系统判断 Agent 可能陷入困境——已执行 2 次 Checkpoint 但仍未修复、累积字符超过 160K、或剩余修复预算不足 20%——触发最激进的压缩。证据摘要全部删除，工作集中的假设/证据从 5 条砍到 2-3 条。设计意图：到了最后关头，强迫 Agent 基于有限的精选数据做出最终决策。

**代价与保障**：Checkpoint 和 Deep 级别清空对话历史后，所有中间推理细节永久丢失——这是主动取舍。但每个级别都在重置时同步最新的修复历史和保护不变量，确保 Agent 从不丢失"我试过什么、什么有效、什么有害"的关键知识。

### 3.3 上下文包：压缩后的信息载体

上下文包（Context Pack）是整个上下文管理系统的核心数据结构。它在每次压缩和每步循环中被注入 prompt，是 Agent 在压缩后唯一的知识来源。

上下文包包含六个部分：

| 信息类别 | 内容 | 更新频率 |
|---------|------|---------|
| 任务框架 | 当前目标信号/时间/suspect block、自动化诊断、受保护不变量、不安全方向、下一步建议 | 每轮刷新 |
| 时序证据 | 首次 DUT/ref 差异的精确记录（信号名、时间点、ref/dut 值、采样模式、驱动赋值类型、suspected block 的行范围） | 每次分歧分析后刷新 |
| 证据摘要 | 最多 5 条经过压缩的证据项（trace、divergence、causal memory、spec 引用、长期记忆），每条只含短结论和 artifact 路径 | 每轮刷新 |
| 因果记忆摘要 | 最近 5 次修复尝试的结构化记录（效果、metric 变化、教训）、有希望的方向、受保护不变量、不安全方向、选中的长期记忆案例、负面模式 | 每次 patch 后刷新 |
| 活跃工作集 | Agent 主动声明的状态：正在验证的假设、锁定的证据/代码片段/spec 条款、已确认的波形事实、已排除的假设、候选编辑位置、缺失证据列表 | Agent 显式声明 |
| 原始 artifact 引用 | 各数据源的路径（RTL、仿真输出、trace 报告、spec、patch journal、记忆索引） | 会话初始化时固定 |

**关键设计**：上下文包中的数据（受保护项、禁止方向、修复账本）不是人工标注的，而是从补丁日志中**自动推导**的。Agent 的活跃工作集（active_working_set）则来自 Agent 在诊断 JSON 中显式声明的状态——系统会从连续的 assistant 回复中提取假设、证据引用和候选编辑位置，累积到工作集中，使得压缩后 Agent 不丢失"我正在验证什么、我排除了什么"的结构化进度。

### 3.4 观察预算：防止分析瘫痪

LLM 有一个常见的行为模式：面对复杂问题时，倾向于不断收集更多信息而不做出决策。在 RTL 修复场景中，这表现为持续调用读工具（read_context、probe_vcd、search_context）而不调用 apply_patch。

观察预算通过一个简单的计数器机制解决这个问题：每做一次只读观察，计数加一；每执行一次写操作（apply_patch/replace_block/record_correction），计数归零。当观察计数超过上限（默认 16 次），所有观察类工具被直接拒绝，强制 LLM 在现有证据基础上执行修复动作或结束回合。

与三层压缩的配合：Light Consolidation 会重置路由相关的计数器但不重置观察预算；Checkpoint Compact 彻底重置所有计数器包括观察预算。这确保了压缩后 Agent 不会被立即封堵。渐进施压曲线（温和提醒 → 强烈催促 → 直接拒绝）在每轮 continue prompt 中通过观察预算倒计时和对应的压力措辞传递给 LLM。

### 3.5 上下文包的注入策略

初始 prompt 中**故意不注入**完整的 spec 全文、contract JSON、corrections 列表和 memory snapshot。这些大段数据被显式删除，仅通过上下文包中的路径引用和结构化摘要间接呈现。初始 prompt 包含：模块元信息、上下文包摘要（任务框架 + 时序证据 + 证据摘要 + 因果记忆）、原始 artifact 路径引用、仿真失败摘要行、trace 分析结果，以及明确的策略指导（优先使用调查子代理、按需精确读取）。

每步 continue prompt 中，上下文包被刷新为最新版本（反映最新修复记录），同时注入观察预算倒计时和对应的压力提示。Compact 后则注入压缩版的上下文包摘要（在 Deep 模式下进一步削减），并配合六条恢复规则指导 Agent 从压缩状态恢复工作。

## 四、工具与子代理设计

### 4.1 工具分层

系统将工具按职责和权限分为三层：

**观察层（10 个工具）**：用于信息收集，不产生任何副作用。
- 通用读取类：`read_context`（8 种读取模式，覆盖仓库树/文件/行范围/spec/TB/阶段产物/trace 报告/修复日志）、`search_context`（正则搜索 RTL/TB/spec）、`query_rtl_kg`（4 种固定知识图谱查询模板）
- 规格类：`read_spec`、`retrieve_spec_block`
- 波形类：`list_vcd_signals`、`probe_vcd`
- 检查类：`run_check`（lint / module_sim / trace_summary / first_divergence）
- 委托类：`route_debug_context`（启动调查子代理，详见 4.7 节）
- 记忆类：`read_long_term_memory`（读取跨会话长期记忆文件的完整内容）

**动作层（2 个工具）**：每次执行都会触发完整的验证-回滚流水线。
- `apply_patch`：自由行范围补丁，支持单次提交多个协调修改
- `replace_block`：替换完整的 always/assign 代码块

**元操作层（1 个工具）**：不修改代码，但影响修复流程。
- `record_correction`：记录上游规划修正，写入叠加层而不修改原始 stage 产物

### 4.2 工具的三层处理架构

每个工具调用经过三层处理，实现了关注点的清晰分离：

**第一层 —— 横切检查：** 进行预算验证、上下文门控。如果观察预算已耗尽，直接在此拦截，返回结构化记忆摘要而非错误信息。

**第二层 —— 业务逻辑：** 执行工具的实际功能。包括路径安全检查、文件读取、知识图谱查询、仿真运行等。

**第三层 —— 横切记录：** 将工具调用和结果写入完整的审计日志（用于事后分析和回放），更新上下文压缩的字符计数，更新观察预算的计数器。

### 4.3 补丁验证流水线

应用补丁不是简单的文本替换，而是一个完整的**验证-回滚**流水线：

1. **前置校验**：检查补丁目标的合法性（只允许编辑当前模块的 RTL 源代码）、范围有效性（行号不越界）、内容安全性（不涉及被保护的路径如规格文件/测试平台/知识库）

2. **证据门禁**（详见 4.4 节）：确保 LLM 在修改代码前已经收集了足够的证据

3. **保护检查**：如果补丁可能影响之前成功修复中建立的不变量，系统要求 LLM 显式声明它已经检查过这些不变量，并提供了保护计划。否则拒绝执行。

4. **文件快照**：在修改前后各创建一份文件副本，用于事后比对

5. **原子应用**：按行号逆序应用所有修改（保证行号不会因前置修改而漂移）

6. **自动验证**：
   - 第一关：Lint 检查。通不过→自动回滚到修改前的状态
   - 第二关：如果是语法修复模式，Lint 通过即为成功
   - 第三关：运行模块仿真。mismatch 数量退化→自动回滚。首次失败时间提前→自动回滚

7. **效果分级判定**：不是简单的通过/失败二分，而是六级分类
   - **通过**：仿真通过，mismatch 归零。终极目标。
   - **改善**：mismatch 数量减少，或首次失败时间推后。虽然是局部改善，但补丁予以保留。
   - **中性**：仿真结果没有统计学意义上的变化。可以保留，但连续三次中性的补丁会被自动回滚（防止 LLM 做无意义的微调循环）。
   - **退化**：mismatch 增加或失败时间提前。自动回滚。
   - **语法失败**：Lint 不通过。自动回滚。
   - **拒绝**：在前置检查阶段就被拦截，根本没有执行。

### 4.4 证据门禁：六道硬性关卡

这是整个工具设计中最关键的安全机制。在补丁工具真正执行之前，系统强制要求 LLM 必须满足六个前置条件：

1. **已阅读当前 RTL 源代码** —— 不能对着旧代码或凭空猜测做修改
2. **已查看 Trace 或仿真结果** —— 必须基于实际的错误证据，不能凭想象
3. **已查看测试平台/规格/知识图谱中至少一种** —— 必须理解设计的预期行为
4. **（功能修复模式）已调用第一分歧点分析** —— 必须知道 DUT 和参考模型的确切差异
5. **（功能修复模式）已阅读规格或阶段产物** —— 必须基于设计意图做修改，不能只看波形
6. **保护不变量检查** —— 如果编辑可能影响之前成功修复中建立的受保护信号或高耦合 block，必须显式声明已检查这些不变量并提供了保护计划

这六道门禁的核心思路是：**不依赖 LLM 自觉遵守行为规范，而是在基础设施层强制执行**。前五道控制"能不能动手"，第六道控制"动手时要不要额外小心"。

### 4.5 从补丁日志到因果记忆：自动化的经验学习

每次补丁尝试被持久化到补丁日志中，包含完整的修改前后对比、**逐信号** metric delta、效果分类和教训总结。系统通过分析这些日志自动构建因果记忆：

- **修复账本**：最近 5 次尝试的结构化记录，含 hypothesis、effects、per-signal delta、lesson
- **受保护的不变量**：从 improved/passed 的补丁中自动提取。通过关键词匹配（如在 hypothesis 和 changed_signals 中检测 "ack_out"+"SETUP"）和信号名直接匹配，逐条生成保护规则
- **禁止尝试的方向**：从 regressed/syntax_failed 的补丁中提取。对于 replace_block 操作额外记录 block_id，防止同样的大范围替换被重复尝试
- **有希望的方向**：从 improved 的补丁中提取，附带 metric delta 供 Agent 判断是否值得继续
- **高耦合 block**：通过统计补丁涉及的信号数量（≥6 个信号的 block 标记为高耦合），要求编辑时提供额外保护计划
- **负面模式**：从长期记忆中类型为 negative_direction 的条目中提取，跨会话共享

**per-signal delta 的关键作用**：传统方案只看全局 mismatch 总量变化来判断改善/恶化。但全局判据的盲区在于——控制信号改善了 99% 但被数据通路信号的回归淹没时，全局总量可能上升，系统会错误地判定为"退化"并回退。per-signal delta 使得系统能够区分"全面恶化"和"部分改善但被其他信号抵消"，为逐信号改善的保留提供依据。

### 4.6 回退策略：五级判据

补丁应用后经过完整的验证流水线，系统用五个层级判据决定保留还是回退：

| 优先级 | 条件 | 行为 |
|--------|------|------|
| 1 | Lint 失败 | 必回退 |
| 2 | 全局 mismatch 总量增加 | 回退（但 per-signal delta 会记录哪些信号改善了） |
| 3 | 首次失败时间提前 | 回退 |
| 4 | 连续 3 次 neutral（无效果） | 回退，防止无意义微调循环 |
| 5 | 局部改善（mismatch 降低或 fail_time 推后） | 保留，继续此方向 |

判据 1-3 使用全局指标，判据 4 使用历史累积，判据 5 是唯一允许保留的条件。系统的保守策略是"宁可错杀也不要保留可能退化的修改"，但 per-signal delta 数据会被完整记录在补丁日志中，供 Agent 在后续轮次中参考——即使一次改善被回退了，Agent 仍然知道"这个方向对某些信号有效"。

### 4.7 调查子代理（DebugInvestigator）

系统引入了一个关键的架构创新：将"收集并分析证据"外包给一个独立的 LLM 子代理。

**动机**：主代理直接调用原始读工具时，每次返回 10-20KB 的原始数据全部堆积在对话历史中，10-15 次调用就能产生 200KB+ 的上下文。子代理的核心思路是**关注点分离**——子代理在自己的独立上下文窗口中调用工具、分析结果，最终只把一份 <3000 字符的分析报告返回给主代理。

**激活条件**：子代理仅在主代理提供聚焦参数（关注信号名、怀疑 block ID、缺失证据类型）时启动。空参数调用（如系统自动刷新上下文包）只走确定性数据打包路径，不浪费 LLM 调用。

**工具权限**：子代理拥有 12 个只读工具（与主代理的观察层相同），但有两个硬性约束——最多 6 次工具调用（强制精选），不可提议 patch（系统提示明确禁止给出具体修复方案）。

**输入**：一份约 500 字符的简洁调查简报——模块名、差异信号/时间/值、采样模式、首要怀疑 block、trace 诊断、调查目标、聚焦参数。子代理不继承主代理的对话历史。

**输出**：一份纯文本分析报告（<3000 字符），包含关键证据（含行号和信号值）、最可疑的 RTL block 及原因、spec 与 RTL 的不匹配、下一步调查建议。报告在工具返回中以顶层字段 `router_analysis` 暴露，主代理首先阅读此字段，需要时再用定向工具做精准补充。

**双层架构**：当 LLM 可用时，启动独立的 LLM 实例做自主推理和工具选择；当 LLM 不可用时，降级为确定性规则脚本（有 focus_blocks→读 RTL 行、有 focus_signals→probe VCD、有 "spec" 在 missing_evidence→检索 spec block）。两层输出格式相同，主代理不感知差异。

## 五、认知框架：Prompt 设计原理

### 5.1 五阶段思维流水线

System Prompt 将修复过程组织为一条强制的认知流水线，每阶段对应一类明确的行为：

| 阶段 | 目标 | 核心约束 |
|------|------|---------|
| 信息收集 | 建立对问题的完整认知 | 跨模块问题查知识图谱，根因不明查波形，功能模式必须先跑分歧分析 |
| 因果诊断 | 将模糊的"仿真失败"转化为可操作的诊断结论 | 每次行动前必须填写诊断 JSON，明确失败类型、根因信号、参考值与实际值的差异 |
| 记忆检索 | 不重复过去的错误 | 检查已有的受保护项和禁止方向，有相似失败记录时必须有新证据才能重试 |
| 范围决策 | 选择与根因精准匹配的修复粒度 | 一行、多行协调修改、整块替换都可以，唯一标准是"直接对应根因" |
| 执行 | 在约束内完成修复 | 只能通过指定工具修改代码，规划层问题走纠正记录而不是直接改 RTL |

### 5.2 诊断 JSON：强制 LLM 结构化思考

嵌入在 System Prompt 中的诊断 JSON 模板是整个认知框架的核心。它在每个行动步骤前强制 LLM 回答 10 个问题：

1. **失败类型** —— 迫使 LLM 将模糊的"仿真失败"映射到具体的 bug 类别
2. **怀疑的模块/文件/信号** —— 迫使 LLM 缩小排查范围
3. **根因信号** —— 迫使 LLM 找出最早的出错信号
4. **第一分歧时间** —— 迫使 LLM 做精确的时间定位
5. **参考值 vs 实际值** —— 迫使 LLM 量化差距
6. **偏差分类** —— 迫使 LLM 区分时序错误和逻辑错误
7. **证据清单** —— 迫使 LLM 为其诊断提供依据，防止幻觉
8. **受保护项检查** —— 迫使 LLM 关注不能破坏的已有改善
9. **保护计划** —— 迫使 LLM 主动思考如何保护已有行为
10. **下一步行动决策** —— 迫使 LLM 做出明确的行动选择

这个 JSON 模板本质上是一个**调试工程师的思维清单**。它不是在"帮助 LLM 更好地回答"，而是在"规定 LLM 必须以什么方式思考"。

### 5.3 领域知识注入

Prompt 中包含了三条关键的领域知识——它们是 RTL 调试专家才知道的"经验法则"：

**规则一：区分测试平台指标和 RTL 信号。** 仿真日志中大量的 `errors_*`、`errortime_*`、`tb_match*` 信号是测试平台层面的统计指标，不是根因级别的 RTL 信号。LLM 如果不理解这一点，会在错误的信号上浪费大量时间。

**规则二：边缘采样不匹配的特殊处理。** 当 DUT 和参考模型的稳定值一致，但在测试平台采样边缘不一致时，问题几乎可以确定是阻塞/非阻塞赋值语义或 `#1` 延迟的差异。这条规则给了 LLM 一个诊断捷径。

**规则三：编辑范围以一致性为准，不以最小化为准。** LLM 通常有"越少改动越好"的偏见。这在软件工程中通常是正确的，但在 RTL 修复中，如果根因需要一次语义一致的重构（比如重写一个 always 块的默认值策略），分多次小改反而会引入新 bug。这条规则明确告诉 LLM：保持语义一致性比压缩改动行数更重要。

### 5.4 权威来源声明

初始消息中包含一句明确的声明：**"测试平台和原始模块规格是本次修复会话的权威来源。"**

这句话建立了一个不可协商的层级关系：规格 > 阶段产物（规划假设） > RTL > LLM 的猜测。如果 RTL 代码和规格文档有冲突，改 RTL。如果阶段产物和规格有冲突，记录纠正。LLM 不应该质疑规格的正确性。

### 5.5 修复模式的分叉

系统支持两种修复模式，产生完全不同的行为路径：

**语法修复模式：** Lint 通过即为成功条件。LLM 被引导关注编译错误、接口定义、宏缺失、声明缺陷和 Verilator 诊断信息。不需要仿真验证，不需要分歧分析。

**功能修复模式：** 仿真通过（mismatch 归零）才是成功。LLM 被要求先建立语义意图（读规格），再定位事实（trace/VCD），再做因果推理，最后执行。证据门禁的五道关卡在功能模式下全部生效。

这确保了在语法修复中不会进行过度复杂的分析，而在功能修复中不会跳过关键的证据收集步骤。

### 4.8 长期记忆系统

系统维护一个跨会话的长期记忆库，使 Agent 能够从历史调试经验中学习。

**存储**：记忆以 Markdown 文件形式存储在 `rtl_memory/` 目录下，按类型分四个子目录——`cases/`（修复案例，improved/passed 的正面经验）、`patterns/`（负面模式，regressed/syntax_failed 的失败教训）、`corrections/`（规划修正，上游阶段的错误记录）、`rules/`（合并规则，Stage6 的结构性经验）。每条记忆由 YAML 元数据头（machine-readable，含 module/signals/failure_type/alignment/confidence/trigger_signals/anti_trigger 等 20 个字段）和 Markdown 正文（human/agent-readable，含触发条件、不适用条件、补丁模式、验证特征、复用约束）组成。`MEMORY.md` 是自动维护的人类可读索引。

**写入**：通过确定性规则蒸馏器（不依赖 LLM）自动触发。每次 patch 执行后，系统判定效果是否值得记录（passed/improved/regressed/syntax_failed 才写入，neutral 忽略），推断失败类型（通过关键词匹配：timing/late/edge→timing_bug，interface/port→interface_bug，logic/value→local_logic），构建元数据和结构化正文，写入对应子目录并重建索引。规划修正调用和合并报告也会分别触发对应类型的蒸馏。

**召回**：采用 LLM 语义选择为主、规则多维打分为降级的双层架构。LLM 路径将候选记忆简化为 `{path, description}` 对，由 LLM 根据描述的语义相关性选择最匹配的 3-5 条——这解决了规则引擎无法覆盖的"跨类别语义关联"问题（如一条标注为 interface_bug 的记忆在原理上对当前的 timing_bug 也有参考价值）。LLM 不可用时无缝降级到多维打分（模块名 +5、信号交集 +2/个、失败类型 +2、时序对齐 +2、置信度 +confidence、反触发 -1）。选中的记忆以摘要形式（body_excerpt 前 2400 字符 + 结构化元数据）进入上下文包；Agent 如果需要更多细节，可通过 `read_long_term_memory(path)` 按需获取完整原文。反触发机制确保记忆在明确标注的不适用条件下被降权。

## 六、设计原则总结

### 6.1 信任但不依赖

系统信任 LLM 的推理能力（通过复杂的 System Prompt 和诊断 JSON 框架引导其思考），但不依赖 LLM 的自觉性（通过工具层的证据门禁和观察预算硬性约束其行为）。

### 6.2 信息密度分层

不是给 LLM 越多的上下文越好，而是根据信息的半衰期做分层处理。原始对话（半衰期短）→ 在压缩时丢弃。结构化摘要（半衰期长）→ 在压缩时保留。磁盘日志（半衰期最长）→ 一直保留，LLM 只在需要时通过工具读取。

### 6.3 压力模型渐进收紧

观察预算从"温和提醒"到"强烈催促"到"直接拒绝"，形成渐进的压力曲线。LLM 有充分的机会根据压力调整策略，但最终会被强制行动。

### 6.4 自动化的经验积累

受保护项、禁止方向、有希望的方向、高耦合模块——这些"记忆"不是人工标注的，而是从补丁日志中自动导出的。系统在一步步的修复尝试中自己学会了"什么该保护"和"什么不该重复"。长期记忆系统将此扩展到跨会话范围，使得不同 debug 会话之间的经验可以复用。

### 6.5 原子操作保证一致性

每一次修改（无论是行级补丁还是块级替换）都是原子操作：应用→验证→回滚（如果需要）作为一个不可分割的整体。外部永远看到一致的状态——要么是修改前的干净版本，要么是验证通过的修改后版本。

### 6.6 上下文隔离与关注点分离

调查子代理在自己的独立上下文窗口中工作，其工具调用产生的几十 KB 原始数据不进入主代理的上下文。主代理只收到一份 <3000 字符的分析报告。这种架构模式将"收集并分析证据"和"基于证据做决策"解耦，避免了单一的 LLM 同时承担两个职责时上下文爆炸的问题。

### 6.7 渐进式压缩防止过早失忆

三层压缩（Light→Checkpoint→Deep）确保 Agent 在形成初步诊断之前不会被强制清除对话历史。Light 层只刷新数据不丢对话，Checkpoint 层需要 Agent 已获取真实差异数据才触发，Deep 层仅在极端困境下启动。每层压缩时都同步最新的修复历史和保护不变量，确保 Agent 从不会丢失"我试过什么、什么有效、什么有害"。压缩只是忘记怎么推理的，不是忘记了结论。
