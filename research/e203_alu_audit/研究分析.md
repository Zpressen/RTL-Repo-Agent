**研究结论：这个案例暴露的核心不是单纯“测试不够多”，而是合法系统行为没有被充分激活，以及评测判据没有准确对应规格契约。**

本次分析基于实际源码检查、仿真复现、合法指令反例和评测器对照实验。原始 spec、生成 RTL、官方 RTL、官方 TB 均未修改；实验只修改临时副本。所有数字均对应 2026-09-10 的本地文件版本，工具为 Verilator 5.044。输入哈希见 [input_manifest.json](input_manifest.json)。

建议将论文问题凝练为两类：

1. **Transactional Activation Gap，事务激活缺口**：信号或代码被执行，不代表合法指令、完整状态序列及跨接口交互被执行。
2. **Contract–Oracle Misalignment，规格契约与判定器错位**：判定器可能过度约束无效周期和参考实现细节，同时漏掉系统级副作用、顺序和完成义务。

固定评测轨迹与可见 golden 波形形成的反馈过拟合，是放大这两类问题的机制；不宜仅用“模型不够强”解释。

**一、复现实验与证据边界**

研究对象是 `system_task/e203_exu_alu_hard` 这一系统生成任务，以及用户指定的两套输出。官方依赖来自 `e203_hbirdv2/e203_exu_alu/verification`。本地任务的 public TB 与该目录的 TB 经 `cmp` 核对完全相同。

另外编写了一个很小的激励器，使用官方 `e203_defines.v` 构造合法 decode，关闭取指异常，提供就绪信号，保持指令直到 golden 完成。每个用例独立复位，驱动位于下降沿，观察在信号稳定后进行。结果同时对照手算期望和 golden。

Codex 的 ADD 错误可以直接追到根因：官方定义 bit 3 是 RV32，bit 4 是 ADD；Codex 却把 bit 3 当 ADD、bit 4 当 SUB。合法 32 位 ADD 同时激活了其加减结果 OR：`(7+5) | (7-5) = 12 | 2 = 14`。参见 [Codex ALU](</home/mokita/RealBench/system_expriment/e203_exu_alu_hard/e203_alu_comb.v:27>) 和 [官方字段定义](</home/mokita/RealBench/e203_hbirdv2/e203_exu_alu/verification/e203_defines.v:329>)。

用户 agent 的错误有系统集成特征：上游把 `integer_decode_info[7:4]` 直接作为算术 opcode，ADD 得到 1；下游 shared datapath 将 opcode=1 解释为减法，因此输出 2。单看两个模块，都能找到“算术模块”和“ADD/SUB 功能”，但模块之间没有一致的编码契约。参见 [上游](</home/mokita/RPG-ZeroRepo/rtl_outputs/e203_exu_alu_system/.zerorepo/workspace/merged/e203_exu_alu_int_branch.v:132>)、[下游](</home/mokita/RPG-ZeroRepo/rtl_outputs/e203_exu_alu_system/.zerorepo/workspace/merged/e203_exu_alu_shared_arith.v:185>)。

用户 agent 的 CSR 路径在立即数形式下选用了 `i_imm`，而规格和 golden 使用 `i_info` 中的五位 zimm。接口名字相近不等于语义一致。参见 [CSR operand](</home/mokita/RPG-ZeroRepo/rtl_outputs/e203_exu_alu_system/.zerorepo/workspace/merged/e203_exu_alu_csr_nice.v:72>)。

因此，“更完整的模块层次”“代码量更多”“各模块看上去实现了功能”，都不能替代系统连接处的语义验证。

**三、第一类：事务激活缺口**

官方 stimulus 的输入只有 `clk` 和 `tb_match`，没有 instruction-ready、LSU command handshake、NICE request handshake 等环境反馈。主体为全零、全一，以及 100 组全输入 `$urandom`，每组保持两拍。参见 [stimulus](</home/mokita/RealBench/e203_hbirdv2/e203_exu_alu/verification/e203_exu_alu_stimulus_gen.sv:129>)。

这不是一个正常的处理器执行环境模型：

- **解码合法性没有建模。** `i_info` 是已经解码的控制信息，不是任意 32 位指令字。独立随机位可能同时开启 ADD/SUB、多个 AMO 子操作、乘和除，或选到未配置的组。
- **异常屏蔽造成有效激励稀释。** `i_ilegl/i_buserr/i_misalgn` 随机，任意一个为 1 就覆盖正常分组。按独立均匀位近似，正常且 valid 的概率只有 `(1/2)×(1/2)^3=1/16`。再选中八种编码中的某一组，100 组向量的期望只有 `100/128≈0.78` 组，尚未要求该组内部 decode 合法。
- **时序深度不足。** spec 要求 valid 输入在 handshake 前保持稳定；乘法需要初始拍加 16 个执行拍，除法更长。每两拍无条件换输入，无法保证一条多周期指令走到结果阶段。
- **环境因果关系缺失。** LSU response 与请求独立随机；NICE completion 不由已接受的 NICE request 产生。随机响应电平不是合法事务完成。
- **跨阶段事件没有系统安排。** 多周期运算末拍反压、AMO 两次响应的错误组合、flush 所处阶段、队列非空时的新事务，需要构造状态序列，不能靠单拍信号翻转代替。

此外，当前 verifier 固定使用 canonical headers，只编译一个配置。官方 `e203_defines.v:161` 中 `E203_HAS_CSR_NICE` 处于注释状态，公开 TB 的 53 个输出也不包含这组可选 CSR NICE 端口。这是配置覆盖边界：若任务只要求默认配置，则可选模式应标为范围外；若宣称实现完整参数化系统，则需要额外配置构建和测试，不能把默认配置 PASS 外推到所有模式。

对默认公开测试增加仅观察、无驱动的计数器后，两候选看到同样的 golden 轨迹：

| 观察项 | 实测 |
|---|---:|
| TB 总采样周期 | 222 |
| reset 释放后的 i_valid 周期 | 93 |
| 其中被取指异常覆盖 | 85 |
| 未被取指异常覆盖的 valid 周期 | 8 |
| valid 且正常选择 ALU / BJP / CSR | **0 / 0 / 0** |
| valid 且正常选择 AGU / MULDIV | 2 / 2，均无输入完成 |
| LSU command handshake | **0** |
| LSU response handshake | **103** |
| NICE request handshake | **0** |
| MULDIV 有效写回 / AMO 有效写回 | **0 / 0** |

8 个正常 valid 周期还包含 NICE 组和未使用的组 7。NICE 组有输入完成，但没有 accelerator request handshake，不能据此说测试了正常自定义指令执行。统计细节见 [公开监控摘要](codex_public_summary.log)。

监控还记录到 13 次“前一拍 valid 且未 ready、当前无 flush_pulse 时输入撤回或 payload 改变”；这一计数只是简化诊断，不作为覆盖所有 flush 例外的完整协议证明。**零 LSU 请求却接受 103 个响应、零正常 ALU valid 周期**，已经是更直接、无需复杂解释的证据。

所以这个案例比“除零边界没测到”严重：默认 PASS 根本不要求完成一次正常加法或一次 memory command。

RTL 中的行覆盖也无法解决全部问题。组合逻辑可以在 invalid 周期求值，多热 decode 可以让多条算术支路都被计算，flush 可以反复触发状态清理；这些都可能增加代码活动，却没有形成有意义的完整事务。这里没有重新测得该任务的 100% 行覆盖，不能声称“本实验实现了 100% coverage 仍失败”；能确定的是，当前 verifier 未将功能覆盖义务或事务完成数量纳入 PASS 条件。

**四、第二类：规格契约与判定器错位**

公开 TB 每个上升沿比较 53 个输出，包含 commit、writeback、LSU、NICE，且没有按各数据端口的有效条件整体区分。其比较公式在确定的二值信号上等价于 golden/DUT 比较。因此，不能将本例描述成“只检查 valid、不检查结果”或“完全没有 assertion”。真正的问题是，它检查的关系并不总等于规格要求的关系。

可以将正确性写成：对所有满足环境假设 A 的输入历史，DUT 满足契约 C。当前公开运行实际验证的只是：对于一个固定输入历史 τ，全部被采样的原始输出与 golden 相同。前者涉及合法性、完整历史、事务边界与可观察义务；后者只是有限轨迹相等。

**方向 A：过度约束，误拒规格上应允许的输出实现。**

从 golden 构造对照实现，唯一改变为：

```verilog
assign wbck_o_wdat = wbck_o_valid ? original_wdat : 32'b0;
```

所有握手信号、内部状态和 valid=1 时的数据完全保留，仅将 valid=0 时的 payload 清零。按照有效写回接口的事务语义，这不会改变任何写回。

结果：公开 TB **FAIL，12 个 wbck_o_wdat mismatch**；已有 84 场景的 SFMS **100%**，strict 仍失败。定向 strict 中仅该数据端口失配 1581 次，其他 52 个输出零失配。

这证明 strict trace 和事务语义确实存在差别。若 benchmark 明确要求 invalid 周期的数据也与 golden 一致，那它评测的是更强的逐周期实现等价；应在 spec 中明示，不能同时将其当作仅依照接口行为自由实现的任务。并非所有无效周期输出都可任意处理，例如 spec 明确规定的 metadata 透传仍须保留。本对照只涉及写回 payload。

**方向 B：观察范围不足，漏掉非当前功能单元的副作用。**

对已有 `stimulus_hidden_test` 的 SFMS scorer 继续审计，发现 NICE 一组比较被以下条件包住：仅当输入分组为 NICE 或当前 category 为 NICE 时进行。LSU、CSR 也有分组条件。

从 golden 构造另一个仅有单处错误的实现：所有正常功能保留，但合法 ADD 的同时额外拉高 `nice_req_valid`。这是明确违反 spec 11.10 的错误：无关组影响了 accelerator 请求。

实验结果：

| 对照实现 | 公开测试 | 84 场景 strict | 84 场景 SFMS |
|---|---|---|---:|
| invalid 写回 payload 清零 | FAIL | FAIL，仅 wbck_o_wdat 不同 | **100%** |
| ADD 额外发 NICE request | **PASS** | FAIL，仅 nice_req_valid 不同 | **100%** |

第二个变体在定向测试中已有 **9 个 nice_req_valid 失配周期**，却全部被 SFMS 功能分组门控排除。它不是没有激活错误；错误已经传播到外部端口，是观察判据漏掉了。严格比较确实发现了它，所以不能把这项结果说成“整个隐藏测试也 PASS”。问题在于 SFMS 将它与正确 golden 都评为 100%。

变体构造：[prepare_oracle_controls.py](prepare_oracle_controls.py)。结果：[公开非法请求变体](spurious_nice_public.log)、[公开 idle 变体](idle_wb_public.log)、[双对照报告](oracle_controls.json)。

这两个对照非常适合论文：**只收紧全部输出比较，会误拒允许的实现；只按当前功能组筛选比较，又会漏掉跨组副作用。** 正确做法不是全局“更严”或“更松”，而是为不同信号和行为建立正确的有效域。

**五、生成过程为什么会走向不完整实现**

Codex 存在明确的轨迹特化逻辑：

- `mem_addr` 对完整 `i_info==0x56a8e909` 返回固定地址 0x96a60db5。
- `observed_wmask` 对少数完整 i_info 常量查表，其余默认 0001；上方已计算的通用 `base_wmask` 没有用于普通命令输出。
- MULDIV 对 `0x12748c04 / 0x92a304bc / 0x65640534` 返回固定结果，并用 `special_ctr` 复现一个特定输入下的两拍数值变化。
- ALU 也有完整 i_info 常量覆盖结果的分支。

参见 [地址](</home/mokita/RealBench/system_expriment/e203_exu_alu_hard/e203_exu_alu.v:68>)、[写掩码](</home/mokita/RealBench/system_expriment/e203_exu_alu_hard/e203_exu_alu.v:253>)、[乘除特例](</home/mokita/RealBench/system_expriment/e203_exu_alu_hard/e203_alu_muldiv.v:69>)。

[iteration_log.md](</home/mokita/RealBench/system_expriment/e203_exu_alu_hard/iteration_log.md>) 记录了根据参考波形推断字段、修正 invalid 输出、枚举剩余参考/候选转移、映射特定数值直至 PASS。这里可确认的是**评测反馈驱动的轨迹特化**；不需要也不能从源码推断模型是否“有意作弊”，更不等于证明训练集污染。

其机制链条为：

```text
少量固定、缺乏合法事务的激励
        ↓
反馈主要奖励异常路径、默认输出和特定采样值的一致
        ↓
golden 波形提供可直接拟合的目标
        ↓
常量映射与周期补丁就能消除 mismatch
        ↓
公开 PASS 成为停止条件，通用执行语义仍未被验证
```

用户 agent 未必通过同一种方式出错，但同样通过了默认测试。已验证的 one-hot→binary opcode 接口错误表明：模块分解并不能自动保证系统契约一致；并行或分层生成方法需要检查接口编码、操作数来源、valid/ready 组合和工作寄存器所有权，而不只是模块是否存在。

此外，Codex MULDIV 用组合 `* / %` 预先计算结果，再用计数器延迟输出。这样的结构不等于规格描述的迭代共享运算过程。**若迭代架构、资源共享属于必须满足的要求，仅靠黑盒输出仿真不足以验证；若研究只评价接口功能，则不能因内部实现不同就直接判错。** 应明确区分功能、时序、微架构和可综合性几种要求。当前 verifier 是 Verilator 编译仿真，没有执行综合、PPA 或共享资源结构验证。

**六、现有增强测试解决了什么，还没有解决什么**

已有的 84 场景测试值得保留：它构造合法 decode、由 golden handshake 推进输入、让 AMO/NICE 响应遵循请求、设置超时并用场景级二值结果减轻长故障链的重复计罚。本次 golden 自检通过，且捕获了两个候选的大量差异。

但不能把它的实现描述得比代码更强：

- 当前所谓“语义义务”主要是**带有效性/功能组门控的逐周期 golden 比较**，不是独立的指令语义模型、提交事件 scoreboard 或普遍的时序性质证明。
- CSR/LSU/NICE 的分组门控漏掉“未被选择时绝不产生副作用”的负向义务，已由 ADD→NICE 变体实证。
- valid/ready 仍需要与 golden 同周期对应。对于 spec 允许的延迟自由度，它不能直接作为实现无关判据；反之，spec 明确规定 17 拍乘法等时序时，也不能盲目用宽松超时放过错误时序。
- 源码中的 `coverage/rankable` 主要依据场景矩阵和可评价格数，不等同于 coverpoint 命中或完整行为证明。一个命名为“某特征”的场景并不自动证明特征已到达关键观察阶段。
- golden self-check 是必要的工具链一致性检查，但同源 golden/DUT 相等不能证明 stimulus 合法或 oracle 符合规格。两个错误副本也可能相等。
- 六个已有特征突变体有用，但不足以校准全部功能域、交叉副作用、环境协议和允许的等价实现。应追加独立的正向等价变体与负向非等价变体，并保留未参与测试构建的突变体集合。
- 原公开 verifier 是二元 PASS/FAIL，**不是以信号匹配率排名**；信号匹配率出现在后来 hidden-seed/场景诊断中。已有汇报材料把两者混在一起，应在研究中纠正。

匹配率失真的实测例子：100 个 seed 下，Codex 和 agent 均 0/100 PASS，但信号样本匹配率分别为 **99.4386%、99.5779%**。定向测试中 agent 的 micro score 高于 Codex，现有 SFMS 排序却相反。这说明分母、门控和聚合方式会影响排名，不能把匹配率直接当正确性，也不能用一个宏平均数掩盖判据本身的问题。

**七、对 RealBench 的结论应如何限定**

RealBench 原论文明确说明：100% 行覆盖不能保证代码正确，并提供基于 Yosys 和 JasperGold 的形式等价流程。它还区分 module-level 与 system-level，后者要求实现全部子模块。[RealBench 原论文 §II-C、II-D](https://arxiv.org/html/2507.16200v1)

因此，准确的研究陈述应为：**本地这套 system_task 仿真评测存在事务激活和契约判定缺口，公开 simulation PASS 可被功能不完整实现满足。** 不能说“RealBench 从未考虑形式验证”，也不能把 simulation PASS 当 formal PASS。此次脚本只运行 Verilator，未运行原仓库的 JasperGold 验证，也没有核验形式任务的环境假设。

本地 RealBench Git HEAD 为 `d47f017e73838517bcc43e2b02ee6a81e202cbf5`。`system_task` 与 `system_expriment` 在该 Git 快照中为未跟踪的本地目录；因此要区分原始发布版本和当前系统任务改造版。

对 64 个 Git 跟踪的 stimulus 文件做了静态初筛：51 个文件的 stimulus 声明输入只有 clk/tb_match，25 个含“100 向量、两拍保持”的模板特征。结果见 [tracked_stimulus_inventory.json](tracked_stimulus_inventory.json)。**这是扩大审计范围的线索，不是 51 或 25 个任务已被证明存在相同缺陷**；有些任务是纯组合逻辑，也可能存在层次引用或其他环境机制。

系统任务需要特别警惕“直接复用原顶层模块 TB”：将生成责任扩展到全部子模块后，测试若没有相应增加合法多周期和集成场景，就可能只验证了原顶层的分派外壳，没有对新增生成责任形成充分约束。本例正适合用来研究这种责任范围与验证范围的不匹配。

**八、与 SWE-ABS 的关系及真正可以研究的增量**

SWE-ABS 的两阶段分别利用覆盖信息补测试，以及用语义突变体发现并修复判定盲点；其研究也考虑误拒正确替代实现。因此，不能把“使用 mutation”或“同时处理误收/误拒”本身宣称为 RTL 新颖性。[SWE-ABS 原论文](https://arxiv.org/html/2603.00520v1)

RTL 系统任务更有价值的增量在于：

| 软件视角的问题 | 本例中的 RTL 特性 | 方法必须增加的能力 |
|---|---|---|
| 目标代码没覆盖 | invalid 也会计算、多热 decode 会遍历多路、事务未结束 | 协议约束、合法 decode、完成性与状态序列覆盖 |
| 执行后检查不充分 | 错误可能多拍后才到 commit，也可能泄漏到另一接口 | 时序传播追踪、全接口副作用监控、事件对应 |
| 正确替代实现被拒 | invalid payload、非强制周期细节与内部状态实现可能不同 | 明确观察有效域和允许的时序自由度 |
| patch 接口不一致 | 子模块 one-hot/binary 编码、operand 来源、ready 定义不一致 | 从 spec 建立跨模块契约并验证连接处语义 |

可以据此构建两阶段方法，但阶段之间应允许反馈迭代：

**阶段 I：从规格建立合法环境与事务义务，驱动真正的系统行为。**

1. 提取机器可执行的接口字段表：位宽、编码、合法组合、配置，以及其来源。把 decode 定义纳入任务交付，而非要求生成器猜字段。
2. 提取环境假设：稳定输入直到接受；响应对应已接受请求；队列容量；reset/flush 取消规则；必要的公平性和最大延迟。
3. 每个功能义务记录前置条件、触发事件、阶段序列、观察事件、禁止副作用。覆盖以义务为分母，不能以 DUT 文件行数为分母，因为漏掉的功能可能根本没有对应代码。
4. 生成带事务状态的 driver，并监测其自身协议。比如 AMO：第一条读命令→读响应→计算→第二条写命令→写响应→commit；在不同阶段分别组合错误和反压。
5. 使用 cover properties 或显式 monitor 记录每个关键阶段确实到达；区分“触发过”“完成过”“被取消且完成了取消义务”。

**阶段 II：校准观察契约并寻找可区分错误实现的反例。**

1. 建立分层 oracle。数据 payload 根据各自 valid/enable 比较；但 CSR 写使能、LSU/NICE 命令等潜在副作用入口必须在全部相关周期监控，不能因当前场景是 ALU 就跳过。
2. 检查事务关联、结果/metadata、命令数量、顺序、禁止重复提交、禁止响应无 tag 消费、flush 后禁止残留副作用，以及有环境公平性约束的完成性。
3. spec 明确规定的时序严格检查；未规定的时序允许基于事件对齐。使用独立 driver/scoreboard 时，应让各 DUT 接受同一逻辑事务序列，并分别遵守它们的握手，避免把 golden 的输入节奏当成所有正确实现必须接受的节奏。
4. 构造非等价突变体：丢掉 byte-enable、忽略地址立即数、截断符号、交换译码、忘记 flush、重复 issue、丢 tag、跨组误发请求。必须先证明或给出合法规格反例，再统计它是否存活。
5. 构造允许的等价变体：invalid payload 改写、内部状态编码变化、契约允许的结构变化。不能把延迟改动一概视为等价，本例 spec 含具体执行周期要求。
6. 对存活的错误变体找最短合法历史，并根据根因补激励、延长观察或修正判据；对被拒的等价变体修正过度约束。局部可用受约束形式检查生成 witness；对证明超时标为 unresolved，不能视为通过。
7. 保留完整反例工件：spec 条款、环境假设、输入历史、DUT/golden 观察、首次语义分歧、golden 自检和相关 cover 命中。

生成器、增强器、最终测试集应有清晰的信息边界。研发阶段可以用 golden 调试，但最终测试种子、场景组合和评测反馈不应反复暴露给被测生成器；本例特别应比较“只返回 PASS/FAIL”与“提供完整 golden 波形”对轨迹特化的影响。

**九、建议的实验设计与可检验假设**

| 研究问题 | 对照实验 | 主要指标 |
|---|---|---|
| 增加随机 seed 是否足够 | 原始随机 / 更多 seed / 合法事务生成，匹配仿真周期预算 | 合法触发率、完成义务覆盖、确认缺陷数 |
| 系统覆盖是否优于代码覆盖 | 行覆盖引导 / 状态覆盖 / 事务和跨接口义务覆盖 | 相同预算的错误变体检出率及新缺陷类型 |
| checker 是否同时误收和误拒 | 全信号 strict / valid 门控 / 分组门控 / 全系统契约 oracle | 非等价变体存活率、等价变体误拒率 |
| 测试反馈是否促成轨迹特化 | 固定 seed / 隐藏 seed；仅诊断 / 完整 golden 波形 | 公开到隐藏的差距、合法反例失败率、特化逻辑出现率 |
| 分层生成是否解决系统集成 | 同任务多次生成、模块测试与系统测试分开 | 接口编码、operand、握手、状态所有权错误分布 |
| 方法能否泛化 | 在部分 IP/候选上开发，在未见 IP/候选/突变体上评估 | 留出集检出率、误拒率、成本、置信区间 |

推荐同时报告：

- 原公开 PASS 中，被合法、已校准反例推翻的候选比例；这是观察到的失效率下界，不是完整正确性估计。
- 各 spec 义务触发和完成覆盖率，包括交叉功能义务；明确分母和未覆盖项。
- 经确认非等价突变体的存活率，以及经确认等价变体的误拒率。
- 按设计/生成样本聚合的结果与区间，避免把同一个候选的数百个 seed 当独立模型样本。
- 增强成本：编译/仿真时间、形式时间、模型调用量，以及需要人工裁定的 ambiguous/unresolved 数量。

SFMS 可以作为展示层，但每个权重和判据要提前冻结，并附上关键安全义务的独立结果。ADD 偷发 NICE 请求这类错误不应该因为在其他特征上表现好而被平均分掩盖。

这项研究最有说服力的起点，是本次已经证实的三个事实：**公开 PASS 的两个实现连合法 ADD 都可能错误；只改 invalid payload 会被 strict 拒绝；一个明确的跨组副作用错误却能拿到已有语义评分 100%。** 它们分别提供激活不足、过度约束和观察遗漏的可复现证据，比单纯展示“换 TB 后分数下降”更能支持方法设计。
