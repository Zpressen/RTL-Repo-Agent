# RealBench e203 IFU 本地评测审计

## 1. 审计对象与结论边界

本审计比较本地 `system_task/e203_ifu_hard` 上的 Codex 候选和仓库级 RTL Agent 候选。输入文件的路径、SHA-256 与工具版本见 [input manifest](input_manifest.json)，紧凑统计见 [results summary](results_summary.json)。实验未修改候选 RTL、Golden、公开 testbench 或验证脚本。

结论只适用于 2026 年 9 月 15 日的本地任务与候选快照。它不能推断整个 RealBench 的质量，也不能作为两个 Agent 的总体能力排名。公开 stimulus 使用未显式固定 seed 的 `$urandom`，因此默认运行只是一条当日观测，不是稳定通过率。

主要观察如下：

- 当前公开脚本单次复测中，Codex 为 FAIL，本 Agent 为 PASS。
- 显式改为 seed 1–100 后，两者均为 0/100。
- 在 92 个合法场景、3 个 seed 形成的 276 个场景单元中，Codex 通过 65 个、本 Agent 通过 55 个；SFMS 分别为 20.58% 和 19.09%。Golden 自检为 276/276、100%。
- 两份 IFU 代码均未发现 ALU 案例中按完整 32 位输入常量查表的模式；主要风险是波形反馈驱动的控制状态和事件顺序特化。

## 2. 为什么公开随机激励不能代表取指事务

公开 stimulus 依次施加全零、全一和 100 组随机输入，每组保持两个时钟。`cmd_ready`、`rsp_valid`、响应数据、flush、halt、输出 ready 和译码反馈均被彼此独立随机化。因而 response 不一定对应先前已接受的 command，flush/halt 也可能与任意伪响应重叠。

定向测试改为事务驱动：每个场景从 reset 开始，memory response 只由 Golden 已握手的 command 产生，并保持到 ready；场景分别检查 PC 推进、目标路由、命令持久性、跨 lane 组装、输出 backpressure、flush/halt、错误合并和预测预译码。这仍是有限测试，但比独立随机信号更能判断合法事务是否被触发、推进和完成。

完整分类结果见 [targeted summary](targeted_summary.log)。值得注意的是，Codex 在 PC/取指控制和流水控制均为 0%；本 Agent 在流水控制和异常处理分别达到 61.11% 与 50.00%，但 PC、ITCM 和 BIU 三类均为 0%。这说明两者失败结构不同，不能用单一逐信号相似度代替功能结论。

## 3. Codex：轨迹驱动的未完成特化

Codex 的 `iteration_log.md` 明确记录了以公开波形首分歧为依据的修改：

1. 为 reset 与 flush 同拍竞争增加 `reset_recovery_r` 和 `reset_redirect_seen_r`。
2. 为匹配 `inspect_pc` 的可见采样时刻增加一项 `pc_commit_pending_r`，将 PC 提交推迟一拍。
3. 将 PC metadata 与指令 holding 分离，增加独立 pending/valid 状态。
4. 为跨 lane 的第二响应增加 guard，随后将其限制到 flush redirect；最终代码把 `second_guard_active` 常量置零，但 guard 状态仍存在。

这些状态并非仅凭名称就能证明错误；问题在于它们的引入理由直接是固定波形采样差异，而新 seed 和合法事务结果没有支持其泛化。当前 Codex 候选甚至未通过当日默认公开复测，因此准确表述应是“轨迹驱动的未完成特化”，不能写成“公开 PASS 后的过拟合”。

## 4. 本 Agent：从 mismatch 优化到控制轨迹特化

本 Agent 的初始公开仿真有 462 个 mismatch。系统 Debug 共执行 17 次候选验证，接受 12 个版本；接受版本的 mismatch 主序列为：

```text
462 → 402 → 379 → 236 → 180 → 108 → 100 → 98 → 26 → 18 → 10 → 0
```

其中一个接受版本只恢复验证依赖，mismatch 仍为 462。行为修改主要集中在：允许响应完成同拍接受新请求、重建第二条跨 lane 命令的地址与目标、flush 时重定向阻塞的第二命令，以及 stale response 与 halt acknowledgment 的耦合。

最后一次修改将控制器 outstanding 清除事件限定为：

```verilog
stale_response && (phase == FIRST) && !second_command_handshake
```

对应实际逻辑见 [`e203_ifu_fetch_path.v`](../../rtl_outputs/e203_ifu_system/.zerorepo/workspace/merged/e203_ifu_fetch_path.v) 中的 `fetch_stale_rsp_hsked`。该候选恰好把剩余 10 个 `ifu_halt_ack` mismatch 降为 0；完整 trial、接受和回滚证据见 [`codex_events.jsonl`](../../rtl_outputs/e203_ifu_system/.zerorepo/workspace/debug_system/e203_ifu/codex_private/codex_events.jsonl)。

单个窄条件仍不足以单独证明过拟合。这里的证据来自组合关系：所有修改以同一公开轨迹的 mismatch 数和首错时刻为选择标准；最终默认轨迹 PASS；seed 1–100 全败；合法事务中 PC、ITCM、BIU 三类均为 0%。因此可以支持“评测反馈驱动的控制轨迹特化”，但不能推断模型具有作弊意图或发生训练数据污染。

## 5. 与 ALU 的对照

ALU Codex 候选直接对完整 `i_info` 值映射地址、写掩码、乘除结果和特殊周期，属于**数值轨迹特化**；IFU 没有发现同类完整输入查表，而是把固定轨迹中的 reset/flush、第二响应、同拍重发和 halt 顺序写进状态逻辑，属于**控制轨迹特化**。

两者共享同一机制：独立随机信号没有形成合法事务，Golden 逐周期波形却提供密集局部反馈；修复过程因而可以持续降低固定轨迹 mismatch，而无需首先满足一般事务契约。这是“事务激活缺口”在组合数据通路和复杂状态机上的两种表现。
